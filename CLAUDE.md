# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Lunora is a Django 6.1 workspace dashboard (dashboard, weather, calendar, reminders, direct messages, rich-text notes) with a single Django app (`app/`) and a Vite-built notes editor split into ES-module chunks. Third-party Python packages are kept deliberately minimal: `Django`, `Pillow`, `reportlab`, `gunicorn` (production WSGI server), `redis` (production cache backend), `psycopg` (PostgreSQL driver, needed for production and for the ranked full-text note search SQL path), `pywebpush` (Web Push delivery), and `holidays` (German public-holiday generation for the vacation planner, with a stdlib fallback). HTTP calls, iCal parsing, and env loading are still hand-rolled on the stdlib. Don't add further dependencies without asking first.

## Commands

All commands run from the repository root with `.venv` activated (`.venv\Scripts\Activate.ps1`).

```bash
python manage.py migrate
python manage.py runserver
python manage.py check
python manage.py test
```

Single test class / method:

```bash
python manage.py test app.tests.test_notes.NotesTests.test_stale_revision_returns_conflict_without_overwriting
```

Notes editor frontend (Vite ES-module build, entry and hashed chunks committed to the repo):

```bash
npm ci
npm run build
npm test
```

Background automations — due reminder e-mails, Web Push, weekly summaries, external calendar syncs. Exactly **one** loop process per deployment, otherwise mail and push providers and subscribed calendars get hit twice:

```bash
python manage.py run_automations --loop
```

```bash
python manage.py purge_expired_notes
```

Bulk-import official public holidays for the vacation planner over a year range (optionally scoped to one federal `--subdivision`):

```bash
python manage.py import_public_holidays --from-year 2026 --to-year 2027
```

Linting and formatting (config in `pyproject.toml`, `eslint.config.js`, `.prettierrc.json`; enforced in CI):

```bash
ruff check .
ruff format .
npm run lint
npm run format
```

CI (`.github/workflows/ci.yml`, Python 3.14, Node 24) runs, and a PR needs green: `ruff check .`, `ruff format --check .`, `npm run lint`, `npm run format:check`, `python manage.py check`, `python manage.py makemigrations --check --dry-run`, `python manage.py test`, `npm test`, and `npm run build` followed by `git diff --exit-code -- app/static/js/bundles/notes.js` (fails when the committed bundle is stale). Run `python manage.py migrate` after pulling and before handing off work, even when no new migration is expected.

`ruff` needs installing once via `pip install -r requirements-dev.txt -c constraints.txt` (adds `ruff` on top of the production `requirements.txt`). `requirements*.txt` pin only direct dependencies; `constraints.txt` pins every transitive one at the tested version and is passed with `-c` by CI and `scripts/deploy.sh`. After changing any `requirements*.txt`, reinstall without `-c` and regenerate it with `python -m pip freeze > constraints.txt` (Git Bash/Linux — PowerShell 5.1's `>` doesn't write plain UTF-8); a pin that disagrees with `constraints.txt` makes `pip install` fail with a conflict. The hand-written page scripts under `app/static/js/` are linted and formatted the same as `frontend/`, but still loaded as plain `<script>` tags rather than bundled — `node --check app/static/js/weather.js` remains a quick syntax-only fallback when you don't want to run the full toolchain.

## Architecture

### Request layering

`app/views/*.py` handle request flow only. Template data preparation belongs in `app/view_models.py`, validation in `app/forms.py`, and anything external or reusable in `app/services/`.

`app/urls.py` does `import app.views as view`, so **every new view must be re-exported from `app/views/__init__.py`** (both the import and `__all__`) or the URLconf will fail.

Rendered UI strings are German; code identifiers, comments, and commit messages are English.

### Feature flags (`app/services/system_settings.py`)

`SystemSettings` is a forced-singleton row (`save()` pins `pk = 1`) toggled from the superuser-only `/administration/` page. Every gated view calls `feature_enabled("<key>")` first and returns `disabled_feature_response(request, key, json_response=...)` — a 503 HTML page or a 503 JSON body depending on the endpoint kind. `app.context_processors.system_settings` also injects `feature_flags` into every template so navigation can hide disabled areas, and `run_scheduled_tasks` re-checks the same flags. A new gated feature needs all three touch points plus a key in `FEATURE_FIELDS`/`FEATURE_LABELS`.

`normal_login_enabled` is separate: when off, only staff/superusers may authenticate (`EmailLoginForm.confirm_login_allowed`) and registration returns 503. `EmailLoginForm` resolves the identifier as either e-mail or username. Registration is protected by Cloudflare Turnstile (`app/services/turnstile.py`, `verify_registration_token`), which fails closed when `CLOUDFLARE_TURNSTILE_REQUIRED` is on and is skipped when it is off (default: on unless `DJANGO_DEBUG`).

Two-factor login is optional TOTP per profile (`app/services/two_factor.py`, RFC 6238 on the stdlib; the setup QR code comes from reportlab's bundled `qrencoder`). `LunoraLoginView.form_valid` does not log a 2FA user in: it parks `{user_id, backend, next, started_at}` in the session and redirects to `login_two_factor`, which checks a TOTP or one-time recovery code under `select_for_update` (`totp_last_step` blocks replays, recovery codes are stored as SHA-256 hashes and consumed) and throttles wrong codes per account through the cache, so restarting the password step doesn't reset the count. `/admin/login/` redirects to Lunora's login so the admin cannot bypass the second factor. Clearing `Profile.totp_enabled_at` in the admin resets a locked-out user.

`/settings/export/` (`app/services/data_export.py`) streams a ZIP of everything the user owns (JSON per area, notes as Markdown, note/chat attachments, UML documents). A new user-owned model belongs in that export too; secrets such as `calendar_feed_token` and the TOTP fields stay out. The counterpart is the `data_import` form on the same tab (`app/services/data_import.py`, stdlib only): Markdown files become notes through a small block/inline parser whose output still passes `validate_note_document` (a leading `# Title` and the export's byline are taken over/dropped, so exported notes round-trip), and `.ics` files become `appointment` events — `CalendarEvent.import_uid` skips VEVENTs imported before, and `RRULE`s expand into a Lunora series through the stdlib expander `_ics_occurrences` (FREQ, INTERVAL, COUNT, UNTIL, BYDAY with month/year ordinals, BYMONTHDAY, BYMONTH; occurrences keep DTSTART's wall-clock time), minus `EXDATE`s; VEVENTs with `RECURRENCE-ID` replace (or, when cancelled, remove) their occurrence and join the same `recurrence_id`. Rules with other parts (BYSETPOS, BYWEEKNO, …) import their first date and count as `simplified`.

The same "Sicherheit" tab lists signed-in devices and deletes the account. `UserSession` rows (device User-Agent, last activity) are written by `app.middleware.UserSessionMiddleware` after the view runs (so the login request is tracked with its rotated key), throttled to one write per five minutes via a session marker; the sessions themselves stay in Django's DB session store, and rows whose session is gone are pruned in `active_sessions`. Those rows are the per-user index of sessions: "Alle anderen abmelden" (`revoke_other_sessions`) and the administration page's session stats read them instead of decoding the session table (migration 0063 backfilled sessions from before tracking), so keep every authenticated request flowing through the middleware. Only the superuser emergency logout (`logout_other_authenticated_sessions`) still decodes every session on purpose. `delete_account` (`app/services/accounts.py`) relies on the cascade for rows but must delete note/chat attachment files and the profile image itself — it collects them first and removes them in `transaction.on_commit`. A new model holding user files needs adding there. Superusers can't delete themselves from settings.

### Notes (the most involved subsystem)

- Documents are Tiptap ProseMirror JSON in `Note.document`. **Never trust client JSON**: `app/services/note_content.py` re-validates every node/mark against explicit allowlists (node types, mark types, fonts, sizes, line heights, hex colors, size/depth/node-count limits) and derives `plain_text` server-side. `Note.save()` itself derives `checklist_done`/`checklist_total` (taskItem counts, shown as a badge on note list cards) whenever `document` is written, so any new write path stays consistent as long as it lists `document` in `update_fields`. Adding an editor feature means extending both `frontend/notes.js` and that allowlist. Math is a `mathInline`/`mathBlock` node holding a raw `latex` string (length-capped, rendered client-side with KaTeX) validated the same way. KaTeX is dynamically imported on the first formula render; do not turn it back into an eager top-level import.
- Concurrency is optimistic on `Note.revision`. A stale `base_revision` raises `NoteConflictError` → HTTP 409 with `{"error": "revision_conflict", "note": ...}`; the client resubmits with `conflict_resolution: true`. `NoteVersion` snapshots are written on interval/restore/conflict and pruned.
- Pin/archive/color/icon/folder live in `NoteUserState`, not on `Note`, because notes are shared and these are per-viewer — the same shared note can sit in a different folder, or be pinned, for its owner and each person it's shared with. `accessible_notes()` annotates `state_is_pinned`, `state_is_archived`, `is_shared_with_user`, `has_unseen_share`, `state_color`, `state_icon` — query through it (or `get_accessible_note`) rather than `Note.objects` so permission scoping and those annotations stay consistent. `set_note_style` validates `color`/`icon` against `NoteUserState.COLOR_CHOICES`/`ICON_CHOICES` before saving.
- Folders (`NoteFolder`, self-referential `parent`, depth capped by `FOLDER_MAX_DEPTH`) and notes share one ordered tree per user. `move_note_tree_item` handles drag-and-drop moves (`before`/`after`/`inside`/`root`) and re-indexes the affected container via `_reindex_tree_container`; `_validate_folder_move_destination` blocks moving a folder into its own descendant. A note can be created from a built-in template (`NOTE_TEMPLATES`) or a per-owner custom one (`NoteTemplate`, saved from an existing note via `create_note_template`).
- Attachments are stored under `PRIVATE_MEDIA_ROOT` via `private_note_storage`, addressed by UUID `file_id`, and only served through `note_attachment_download`, which re-checks note access. They are never under `MEDIA_URL`.
- PDF export renders server-side with reportlab (`app/services/note_pdf.py`); Markdown export (`app/services/note_markdown.py`) is a plain server-side renderer of the same document. Both go through the normal access check so permissions apply to exports too.
- Search goes through `app/services/note_search.py` (`search_notes`), used by both the notes list and `global_search` — never re-filter with `icontains` at a call site. It dispatches on `connection.vendor`: PostgreSQL matches a weighted `tsvector` (`title` A, `plain_text` B, `german` config) ranked with `SearchRank`; SQLite falls back to substring matching with an equivalent SQL-side rank. Both share `parse_search_query` (bare words AND, `"phrases"`, `-exclusions`) so behaviour matches. Two things are deliberate: terms are matched as `:*` prefixes **and** kept as substrings, because German compounds mean "Rakete" must find "Raketenstart" and "start" must too; and the weighted tsvector is stored in `Note.search_vector` (`SearchVectorField`, GIN index `app_note_search_vector_gin`), refreshed by `Note.save()` via `refresh_note_search_vectors` whenever `title`/`plain_text` are written (PostgreSQL only — on SQLite the column stays NULL and the index isn't created; migration 0071 creates it and backfills conditionally). A raw `queryset.update()` of title/plain_text bypasses `save()`, so call `refresh_note_search_vectors` there; until then such a note is still found through the substring branch. `django.contrib.postgres` is in `INSTALLED_APPS` for the field and index. Terms fed to `search_type="raw"` must stay bare words (`^\w+$`) or PostgreSQL raises a query-time error. Because the test suite runs on SQLite, `NotePostgresSearchSqlTests` compiles the production SQL against a PostgreSQL backend to cover that branch.
- `frontend/notes.js` builds to the ES-module entry `app/static/js/bundles/notes.js` and content-hashed files in `app/static/js/bundles/chunks/`; all of them **are committed**. `vite.config.js` separates editor core, Tiptap extensions, syntax highlighting, and the lazily imported KaTeX renderer. After editing anything in `frontend/`, run `npm run build` and commit the regenerated entry plus the complete chunk directory so stale hashed chunks are removed. `notes.html` must load the entry with `type="module"`, and `lunora/settings.py` keeps `.js` mapped to `application/javascript` for Django's Windows development server. `npm test` (vitest) only covers `frontend/**/*.test.js` — the small pure helpers.
- The editor toolbar (`notes.html`) keeps only the most-used controls (undo/redo/save, bold/italic/underline/strike, lists) always visible; everything else sits behind two `data-toolbar-tab="text"|"insert"` tabs (`activateToolbarTab` in `notes.js`, modeled directly on `settings.js`'s `activateSettingsSection`) toggling sibling `data-toolbar-panel` groups. This works with zero changes to command dispatch because `runCommand`/`applyFormatControl`/`updateToolbarState` already select every control by its `data-command`/`data-format` attribute rather than DOM position — moving a button between panels never breaks it. The code-language `<select>` (`data-code-language-group`) deliberately stays a *sibling* of both panels, not nested inside one, because its visibility is driven by cursor position (inside/outside a code block), independent of which tab is active. `openFormatControl` (used when a keyboard shortcut like Alt+Shift+F targets a `[data-format]` control) activates that control's owning tab first if it's currently hidden, so shortcuts never silently focus a `display:none` element.
- Code blocks get syntax highlighting via `@tiptap/extension-code-block-lowlight` plus individually imported `highlight.js` grammars registered with `lowlight` (StarterKit's own `codeBlock` is disabled via `codeBlock: false`). Do not switch back to `lowlight`'s larger `common` bundle. The toolbar's language options, the registered grammar keys, and `note_content.py`'s `ALLOWED_CODE_LANGUAGES` must stay aligned, or a saved language can either fail highlighting or server-side validation.
- `@`-mentions are a `mention` atom node (`{userId, label}`) built on `@tiptap/suggestion` (no `tippy.js` — the popup is a manually positioned `<div>`, matching `messages.js`'s context-menu pattern). The suggestion list (`note_mention_candidates_api`) and the server-side save-time check (`_validate_mention_references` in `app/services/notes.py`) both restrict candidates to users who already have access to the note (owner + `NoteShare` rows) — mentioning someone without access is rejected, not auto-shared.
- Note-to-note links are a `noteLink` atom node (`{noteId, label}`); `note_link_candidates_api` suggests targets from `accessible_notes()` and `_validate_note_link_references` re-checks the same access at save time, the same pattern as mentions. `save_note` diffs the document's `noteLink` references against `NoteLink` rows (`_set_note_links`) to keep backlinks in sync without a stored reverse index.
- Inline comments are a `commentThread` mark (`{threadId}`, a client-generated UUID) plus `NoteCommentThread`/`NoteComment` rows. `save_note` cross-checks every `commentThread.threadId` found in the document against real `NoteCommentThread` rows for that note, the same way it already does for attachment/mention references — a document can't reference a thread it never created via `note_comments_api`. `duplicate_note` strips `commentThread` marks from the copy (`_strip_comment_marks`) because the new note has no threads of its own yet; forgetting that step makes the duplicate un-savable.
- Public read-only links: `Note.public_token` (null = not public) is managed only by the owner through `note_public_link_api` (`set_note_public_link`; POST on/rotate, DELETE off) and gated by the `note_public_links` flag. `/s/notes/<token>/` (`note_public`, no login) renders the note server-side with `app/services/note_html.py` — a second trust boundary that escapes everything and re-checks styles/colors/link schemes against `note_content.py`'s allowlists, renders mentions and note links as plain labels, and drops comment marks — and its files go through `note_public_attachment`, which only serves attachments of that same note. Both send `Referrer-Policy: same-origin` (not `no-referrer`, which makes browsers send `Origin: null` and fails CSRF for same-origin forms such as logout) and `X-Robots-Tag: noindex`. The token is a credential like `calendar_feed_token`: keep it out of exports, duplicates and logs. Trashed notes and inactive owners 404. Formulas render client-side through the separate Vite entry `frontend/note_public.js` → `app/static/js/bundles/note_public.js`, loaded only when the note contains math; there is no syntax highlighting on the public page.
- Both mentions and comments notify through the shared `NoteActivityNotification` model (`kind` = `mention`/`comment`) — see Notification idempotency below.

### Messages live updates

The messages page is server-rendered; `messages_live_updates` re-renders the same partials in `app/templates/app/partials/` via `render_to_string` and returns them as HTML strings inside a JSON payload that `app/static/js/messages.js` swaps in. The full view and the live view must build compatible template contexts — changing a partial's context requirements means updating both `messages()` and `messages_live_updates()`. The payload also carries a plain-string `typing_label` (built by `_typing_label()` from each `ConversationMember.typing_until`, pinged by the client via `chat_typing_ping`) that isn't tied to any partial — `messages.js` writes it directly into `#typing-indicator`.

Searching one conversation (`?find=`, `_search_conversation_messages`, same query syntax as the note search) lists hits linking to `?around=<id>#hit-<id>`; `_message_before_id` turns `around` into the usual `before` boundary with `CHAT_SEARCH_NEWER_CONTEXT` newer messages kept, in both `messages()` and `messages_live_updates()`, and `messages.js` forwards `around` to the live poll and scrolls to the hash instead of the bottom.

"Weiterleiten" (`form_name=message_forward`, `_forward_chat_message`) copies a message's body and attachment (a real file copy with a new `file_id`, never a shared file) into another conversation from `_forward_targets` (visible to the user, not blocked either way) as the forwarder's own message with `is_forwarded`; the original sender is deliberately not stored or shown. Its dialog lives in `messages.html`, outside the live-updated partials, so only `messages()` builds `forward_targets`.

Polls, scheduled messages and `@`-mentions live in `app/services/chat.py`; the views only dispatch the `poll_create`/`poll_vote`/`poll_close`/`scheduled_action` `form_name` branches into it (`_handle_chat_tool_post`). A poll (`ChatPoll` → `ChatPollOption` → `ChatPollVote`, group chats only) hangs off a normal `ChatMessage` whose body is the question, so previews ("📊 Umfrage: …"), search and pinning keep working; message queries that build previews `select_related("poll")` and the stream applies `poll_prefetch()`. Polls can't be forwarded, and deleting the message deletes the poll. A `ScheduledChatMessage` is a text-only draft with a `send_at`; `deliver_scheduled_message` claims it by deleting the row inside its transaction, so `run_scheduled_tasks` and the page itself (`messages()`/`messages_live_updates()` call `send_due_scheduled_messages(conversation=…)`) can deliver concurrently without doubles, and drops it when the sender can no longer write there (`can_send`). The `datetime-local` field is read in the profile timezone, so its min/max/suggestion come from `schedule_bounds` rather than the browser clock. Mentions are resolved server-side against members' current display names (longest match wins, `@alle` = everyone; usernames are e-mail addresses, so they're not used) by `apply_mentions` after every new message (compose, first message of a new chat, scheduled delivery — not forwards) into `ChatMessage.mentioned_users`, which `render_message_body` uses to escape and highlight the text. They notify through `materialize_chat_mention_notifications` (`chat_mention` inbox rows, source key `chat-mention:<conversation>:<message>`, category `messages`, mailed by `send_pending_user_notification_emails`) regardless of mute, skipping members who blocked the chat; opening the conversation marks them read (`mark_conversation_mentions_read`) and deleting the message removes them (`forget_mentions`). The live-update fingerprint covers votes, closed polls and the user's scheduled messages; the scheduled list is its own live region (`partials/messages_scheduled.html`), while the poll dialog and the `json_script` of mention candidates sit outside the live partials, built only by `messages()`.

"Bearbeiten" (`form_name=message_edit`, `edit_message` in `app/services/chat.py`) reuses the compose field: `messages.js` switches its hidden `form_name` to `message_edit` and enables the `message_id` input, filled from the bubble's `data-edit-body`. `can_edit_message` allows own messages that aren't deleted, forwarded or polls within `CHAT_EDIT_WINDOW` (24 h); an edit sets `edited_at` (already part of the live fingerprint) and calls `update_mentions`, which notifies newly mentioned members, deletes the notification of those no longer mentioned and updates the text of the others.

The message context menu's "Als Aufgabe"/"Als Termin" entries (shown per `feature_flags`) are client-side only: `messages.js` puts `{target, text}` into `sessionStorage["lunora-chat-prefill"]` and opens the tasks page or the calendar, whose scripts move the text into their quick-add field once. Keep it out of the URL — message text must not end up in access logs.

Conversations can be group chats (`Conversation.is_group`, created by `start_conversation` when 2+ recipients are selected); group membership changes via the `member_action` form's `add_member`/`leave_group` actions. Chat messages may carry a single optional file/image/audio attachment (`ChatMessageAttachment`, stored the same way as `NoteAttachment` — see `app/services/chat_files.py`; `validate_chat_upload` checks audio by magic bytes and the stored content type comes from the extension, never from the client). Voice messages are recorded client-side with `MediaRecorder` in `messages.js`, put into the normal attachment input via `DataTransfer` together with a `voice_duration` hidden field, and submitted like any attachment; `chat_attachment_download` answers single `Range` requests with 206 for inline playback because Safari won't play `<audio>` otherwise and an optional `reply_to` (a lightweight quote of another message in the same conversation, not a nested thread) — both ride through the same `messages()`/`messages_live_updates()` context-building helpers (`_build_attachment_item`, `_build_reply_preview`, `_message_preview_text`), so extending one still means keeping both views' contexts in sync.

### Calendar

Events are created in Lunora, imported once from `.ics` files, or mirrored read-only from subscribed external calendars (below). Every `CalendarEvent` carries a `category` (`appointment`/`meeting`/`deadline`/`personal`/`other`, German labels in `CATEGORY_CHOICES`); `CATEGORY_TONES` maps each to one of the existing `tone-*` CSS color classes, so the UI color comes from the category rather than a per-source color. Lunora is a general workspace, not a school app — keep categories and copy generic.

The month grid also shows the user's open tasks on their local due date (gated by the `tasks` flag), sharing each day's three visible slots with events (events first); each task chip is a `task_toggle` form posting to `/tasks/` with `return_to`, the same convention as the dashboard. Vacation-planner data shows up too, gated by the `vacation_planner` flag: `calendar_day_markers` puts holidays (only for years with a `VacationYear`, which carries the federal state) and vacations on each day as thin `day-marker` links into the planner that take no event slot; running and upcoming vacations join the calendar's and the dashboard's "Nächste Termine" lists, and the feed below. Events can span several days through the form's optional `end_date` ("Bis"); `calendar.js` opens the create dialog on right-click (tap on touch screens) or prefills a dragged range as an all-day event. `?view=week|three_days|day&date=<day>` switches to a time-grid view (`_calendar_time_grid` in `view_models.py`, columns per `CALENDAR_TIME_GRID_DAYS`, rendered by `partials/calendar_time_grid.html` with `--week-days` setting the column count): the queried range is the anchor day's month grid widened to the shown days, all-day and ≥24 h events plus markers and tasks sit in an all-day row, and timed events are placed on a 24 h grid by minute, with `_assign_week_lanes` splitting overlapping events into side-by-side lanes. In that grid `calendar.js` turns a right-click or a vertical drag into half-hour slots that prefill the dialog's start/end time. A `view` in the URL is stored as `Profile.calendar_view` (`_calendar_view` in `calendar_views.py`), and `/calendar/` without `view`/`year`/`month`/`date` opens it, so every view-switch link names its view. Own events carry `partials/calendar_event_move_data.html`; `calendar.js` drags them with pointer events (mouse/pen only, so touch keeps scrolling) and posts `calendar_event_move` (`CalendarEventMoveForm` → `move_calendar_event` in `calendar_service.py`): a day drop keeps time and length, a grid drop sets `start_minute`, the bottom strip sets `end_minute`, all in local wall-clock time; a series occurrence moves alone. POST branches redirect to `request.get_full_path()`, so they stay in the current view.

Export goes the other way: `app/services/calendar_service.py` renders a hand-written RFC 5545 feed (`build_calendar_feed` — CRLF line endings, 75-octet line folding, text escaping, `DATE` values for all-day events) — no `icalendar` dependency. `calendar_feed` serves it at `/calendar/feed/<token>.ics` **without login**; `Profile.calendar_feed_token` (null until the user creates a link in settings, rotated/cleared via `reset_calendar_feed_token`/`disable_calendar_feed`) is the only credential, so never log or render it outside the owner's settings page. The feed contains the user's own events (not those of subscribed calendars — re-exporting them would show them twice or loop) plus invitations they *accepted* (declined/pending ones stay out), from `FEED_LOOKBACK_DAYS` ago onwards, plus vacation-planner periods as all-day events; UIDs are `lunora-event-<pk>` / `lunora-vacation-<pk>` so subscribers update events in place. It is gated by the `calendar_feed` flag (disabled → 503, unknown token or inactive user → 404). Google Calendar polls subscribed feeds on its own schedule (roughly every 8–24 h) and ignores `REFRESH-INTERVAL`; that latency cannot be fixed server-side.

External calendars (`CalendarSubscription`, `app/services/calendar_subscriptions.py`, gated by the `calendar_subscriptions` flag) are added on the settings calendar tab with an http(s)/webcal iCal URL, a name and a `.tone-*` color. `sync_subscription` fetches the URL and replaces all of the subscription's `CalendarEvent` rows (`subscription` FK, owner = the user) inside a transaction holding the subscription's row lock, so overlapping syncs don't duplicate; a failure keeps the old events and stores a fixed German message in `last_error`. Parsing reuses `data_import.ics_event_rows` with a `window` (`WINDOW_PAST`/`WINDOW_FUTURE` around now), in which `_ics_occurrences` runs series up to the window's end and skips the periods before it (without COUNT), so old daily/yearly series still reach today; `limit` caps the rows. `run_scheduled_tasks` syncs subscriptions not tried for `SYNC_INTERVAL` (at most `MAX_SYNCS_PER_RUN` per pass); adding one and "Jetzt aktualisieren" (throttled by `MANUAL_REFRESH_INTERVAL`) fetch inside the request. The fetcher is the SSRF boundary: `normalize_url` allows only http/https on the default port, no credentials, no internal host names or non-global IPs, and `_public_connection` replaces `http.client`'s `_create_connection` so the addresses DNS returns at connect time — for the first request and every redirect (`MAX_REDIRECTS`, each re-normalized) — must be global too (no DNS rebinding); responses are capped by `MAX_CALENDAR_BYTES` and `FETCH_DEADLINE_SECONDS`. The URL is a credential: never log it, render it (not even back to its owner), export it or put it into an error message. Subscribed events are read-only: `_calendar_event_manage_fields` gives them `can_delete` false plus `subscription_name`, their tone and category label come from the subscription, and every write path (edit, delete, series delete, `move_calendar_event`) filters on `subscription=None` — keep that for new ones. `_calendar_visible_events_query` drops them while the flag is off and `select_related`s the subscription (a caller that narrows columns with `.only()` must call `.select_related(None)` first, as the year grid does), the data export lists subscriptions without URL and leaves their events out, and the `.ics` import doesn't treat their UIDs as duplicates.

`?view=agenda&date=<day>` lists the `CALENDAR_AGENDA_DAYS` (28) days from the anchor that have events, tasks or planner markers (`_calendar_agenda`, `partials/calendar_agenda.html`), queried like the time grids (anchor's month grid widened to the shown days); `_agenda_time_label` says "ab"/"bis" for multi-day events, and a timed event ending exactly at midnight is not repeated on the next day there.

`?view=year&year=<y>` renders twelve small month tables (`_calendar_year_grid`, `partials/calendar_year.html`) with a per-day busy level from events plus open tasks and holiday/vacation markers; every day links to its day view. An event's `location` is linked through `location_link` in `calendar_service.py` (OpenStreetMap search, or the address itself for an http(s) URL, i.e. a video call) and mirrored client-side by `locationLinkFor` in `calendar.js`. The create, edit and reminder forms share the page, so `CalendarEventEditForm` and `CalendarReminderForm` default to their own `auto_id` prefixes — keep ids unique when adding forms there.

Manual events can invite other Lunora users via `CalendarEventAttendee` (`CalendarEventForm.attendees`, checkbox-multi-select same as `ConversationStartForm.recipient` in Messages). `view_models.get_calendar_context` unions the requesting user's own events with `Q(attendees__user=user)` so invitees see the event on their own calendar (`.distinct()` is required — the join can otherwise multiply an event with several attendees). While the dialogs are open, `calendar.js` sends their date/time fields plus the ticked `attendees` to `calendar_availability` (`CalendarAvailabilityForm` → `attendee_availability`), which returns only a free/busy/away status per person — own events and accepted invitations are busy, a vacation (planner flag on) is away; never return titles or times of other people's events there. Accept/decline goes through the `calendar()` view's `event_rsvp` form_name branch, scoped to the requesting user's own `CalendarEventAttendee` row only.

`/calendar/events/<id>/` (`calendar_event_detail`, `get_calendar_event_detail_context`) is the event's detail page for the organizer and every invitee (`can_view_event`, others 404): facts, invitees with their answers, the own RSVP (same `_respond_to_invitation` as the calendar's `event_rsvp` branch) and `CalendarEventComment`s. Comments exist only on events with invitees; `add_event_comment` notifies `event_comment_recipient_ids` (organizer plus invitees who haven't declined, minus the author) through `materialize_event_comment_notification` (`event_comment` inbox rows, source key `event-comment:<pk>`, category calendar, mailed by `send_pending_user_notification_emails`), authors delete their own (`delete_event_comment` drops the inbox rows too), and posting is gated by `calendar_event_creation`. `_calendar_event_manage_fields` carries `detail_url`, so every event list, the agenda, invited month chips and the edit dialog (`data-detail-url`) link there.

`CalendarEvent.reminder_minutes` (choices `EVENT_REMINDER_CHOICES`) becomes one `CalendarReminder` per event and person — owner plus accepted invitees — via `sync_event_reminders` in `calendar_service.py`, so the existing reminder delivery (inbox, e-mail, Web Push, browser claim) carries event reminders with event texts from `reminder_texts` in `notifications.py`. Call `sync_event_reminders` after anything that changes an event's start, title, reminder or attendees' answers (create/edit forms, `move_calendar_event` and `event_rsvp` already do); a moved reminder is re-armed (notified-at cleared, inbox row deleted), events that already started are left alone, and reminders with an `event` stay out of the hand-made reminder list and the weekly summary.

A manual series is a set of independent `CalendarEvent` rows sharing `recurrence_id` (expanded up front by `expand_manual_recurrence`). Edits and deletes take a `scope` (`this`/`following`/`all`) resolved by `series_scope_events` in `calendar_service.py`; `CalendarEventEditForm.save` moves the other occurrences by the edited one's *local* day shift and re-combines them with the new wall-clock times (so DST changes don't shift the time of day), keeps existing attendees' answers, and gives "following" a fresh `recurrence_id` when earlier occurrences exist. The edit dialog's delete button submits the same form with `name="form_name" value="calendar_event_delete"` (the submitter's value comes last in the POST, so it wins over the hidden field) and its own `data-confirm` — `base.js` reads `data-confirm` from the submit button before the form. The `calendar_quick_add` form (`CalendarQuickAddForm`) creates a one-hour or all-day event from one line of text via the quick-add parser (see Tasks).

### Weather

`app/services/weather_service.py` keeps the OpenWeather key strictly server-side, caches JSON responses for `WEATHER_CACHE_SECONDS`, and proxies map tiles through `weather_map_tile` so the key never reaches the browser. Without a key the whole page falls back to demo data (`_fallback_*` helpers) — new weather features need both the API path and a fallback path, since tests cover the keyless behavior. The initial `/home/` render must remain provider-free: `get_home_context` emits a placeholder and `home.js` fetches the personalized summary from `/home/weather/` only for a visible weather widget, with a ten-minute client freshness guard. Keep that endpoint private/no-store and return JSON feature-flag errors.

### Per-user time and formatting

`app.middleware.UserTimezoneMiddleware` activates the signed-in profile's timezone for each request and deactivates it afterwards. Date/time strings for users must go through `app/services/user_preferences.py` (`format_user_date`, `format_user_time`, `format_user_datetime`, `localtime_for_user`) because format and timezone are per-profile settings, not global ones.

`app.context_processors.appearance_settings` derives the glass-UI CSS variables (accent, overlay alphas, blur) from `Profile` for every template, including anonymous requests. `base.html` sets only `--color-accent` inline; `base.css` derives `--color-accent-strong` from it per theme with `color-mix()` (darker in light mode, lighter in dark mode), so don't set the strong variant inline again — an inline value would override the dark-theme derivation.

`Profile.theme` is `light`/`dark`/`system`; `base.html` renders it as `data-theme-preference` and only a light/dark fallback as `data-theme`, which the inline head script (and `getThemePreference`/`getInitialTheme` in `base.js`, also on `prefers-color-scheme` changes) resolves — CSS only ever sees `data-theme="light|dark"`. `syncThemeColorMeta` keeps `<meta name="theme-color">` on the resolved `--bg-base` after every theme, color-theme, strength or accent change. `Profile.color_theme` (`COLOR_THEME_CHOICES`) is rendered as `data-color-theme` on `<html>` and selects a neutral-palette block in `base.css` (background, text colors, glass surfaces, shadows, solid panel); `sand` lives in `:root, [data-color-theme="sand"]`, every other theme has a light block plus a `[data-theme="dark"][data-color-theme="…"]` block that must set the same properties, or light values leak into dark mode. A new theme needs a `COLOR_THEME_CHOICES` entry (plus migration) and both blocks; its light block also sets `--theme-swatch`, the signature tone of its settings swatch. Theme blocks define the *inputs* `--theme-bg`/`--theme-glass-bg`/`--theme-glass-bg-soft`/`--theme-panel-solid`; `:root` derives `--color-bg`, `--glass-bg`, `--glass-bg-soft` and `--surface-panel-solid` from them by mixing in `--theme-swatch` scaled by `--theme-strength` (`Profile.theme_strength` / 100, inline on `<html>`) and `--theme-mix` (smaller in dark mode) — so never set those four derived tokens in a theme block. The page background is no image: `partials/page_background.html` is an inline SVG of waves (included in `base.html` and `offline.html`) whose fills come from `--bg-base`/`--bg-wave-soft`/`--bg-wave-deep`, derived from the theme's `--color-bg` and the accent. The settings swatches carry `data-color-theme` themselves to preview each palette, so don't scope those selectors to `:root`.

### Design tokens

`base.css` `:root` (with `[data-theme="dark"]` overrides) is the single source for colors, radii and focus states; page stylesheets must not redefine `--color-accent`/`--color-accent-strong` or introduce their own accent palette — every area follows the profile accent. Use `color-mix(in srgb, var(--color-accent) N%, transparent)` instead of hard-coded `rgba(181, 150, 104, …)` tints; `--color-danger`/`--color-success`/`--color-warning` (plus `--color-danger-solid` for filled badges with light text) for status colors; `--color-on-accent` (dark) for text on accent fills — the selectable accents are mid-light, so white text on them fails contrast — and `--color-on-solid` (light) for text on `--color-danger-solid`/warning or dark fills; elements that sit directly on the page background (not inside a `.glass-panel`) need their own `var(--surface-panel)` + `backdrop-filter` surface, or their text becomes unreadable over light parts of the background image in dark mode; `--surface-control`/`--surface-control-hover` for translucent control backgrounds; `--surface-panel-solid` for opaque dialogs/popovers; `--radius-xs` (8) / `-sm` (12) / `-md` (16) / `-lg` (22) / `-pill` instead of ad-hoc pixel radii; and the type scale `--text-2xs` (0.7rem) / `-xs` (0.76) / `-sm` (0.82) / `-md` (0.88) / `-base` (0.95) / `-lg` (1.05) / `-xl` (1.3) / `-2xl` (1.45) / `-3xl` (2) instead of ad-hoc `rem` font sizes — only display sizes (hero titles, clock, big numbers, `clamp()`) and the editor's relative `em` headings stay outside the scale. `DesignTokenTests` in `app/tests/test_core.py` enforces the accent, gold-tint and font-size rules by scanning every stylesheet, so a violation fails CI with its `file:line`. Shared components live in `base.css` too: the `.tone-*` palette for user-picked colors, `.switch`, the custom checkbox, and the `dialog::backdrop` (dialogs containing a `.glass-panel` automatically get the opaque surface). While a modal dialog is open, `html:has(dialog:modal)` locks page scrolling and `dialog *` uses `overscroll-behavior: contain`; `trackPageOverflow` in `base.js` sets `data-page-scrolls` so only pages that really scroll keep their scrollbar gutter (no sideways jump either way). Open dialogs with `showModal()` to get this — `show()` stays non-modal and doesn't lock.

### Accessibility

`app/tests/test_accessibility.py` renders every main page (signed in and public) and fails on a second `<main>`, a missing `<h1>`, duplicate ids, or a form field without an accessible name (`<label>`, `aria-label`/`aria-labelledby` or `title`). Two forms on one page with the same field names must not share ids: give the second one its own `auto_id` prefix in its `__init__` (as `CalendarEventEditForm`, `CalendarReminderForm`, `ConversationStartForm`, `CustomHolidayForm`, `TaskListForm`, `TaskLabelForm` do). Page sidebars inside `<main>` are `<section aria-label>`/`<div>`, not `<aside>`. A `<form>` may not carry `role="tabpanel"`, so settings panels with a form are `<section role="tabpanel">` around a `<form class="settings-panel-form">` (`display: contents`). Every drag interaction needs a keyboard route: dialogs for calendar events, the board's status buttons, Alt+↑/↓ in `tasks.js`, the notes "Verschieben" dialog, dashboard arrows.

### Focus rings on wrapped inputs

`base.css`'s global `input:focus-visible` rule (actually `a`/`button`/`summary`/`input`/`textarea`/`select`/`[tabindex]`) puts a `box-shadow` on the focused element itself, following *its own* border-radius. Several search/text fields render as a borderless `<input>` (`border: 0`, no radius) inside a decorative rounded wrapper div (background + border + border-radius); the same happens to non-input focusable elements carrying `tabindex` (e.g. a `contenteditable` region) inside a rounded container. Focusing the input then draws a square-cornered glow that visibly breaks out of the rounded wrapper. Fix on the wrapper, not the inner element: add `<wrapper>:focus-within { border-color: var(--focus-border); box-shadow: var(--focus-ring); }` and `<wrapper> input:focus-visible { box-shadow: none; }` (swap `input` for whatever the focusable descendant actually is). See `.search-field` (weather.css), `.notes-search` (notes.css), `.reminder-date-field` (calendar.css), or `.note-editor-page` (notes.css — wrapping the `tabindex`-bearing `.tiptap` contenteditable) for reference.

### Notification idempotency

Delivery is "at most once" via columns rather than a queue: `CalendarReminder.email_notified_at` / `desktop_notified_at`, `CalendarEventAttendee.email_notified_at` / `desktop_notified_at`, `NoteActivityNotification.email_notified_at` / `desktop_notified_at`, `Task.email_notified_at` / `desktop_notified_at`, and the `WeeklySummaryDelivery` unique `(user, week_start)` constraint. Desktop notifications are *claimed* by the browser (`claim_due_desktop_reminders`, `claim_due_event_invitations`, `claim_due_note_activity`, `claim_due_desktop_tasks` each use `select_for_update` + a batch update) so multiple open tabs cannot double-notify; `claim_desktop_notifications` (the single `/notifications/claim/` endpoint `base.js` polls) merges all four lists into one JSON response, each gated by its own feature flag. Preserve this pattern for any new notification type.

The persistent inbox is backed by `UserNotification`, which stores one durable row per recipient/source using the unique `(recipient, source_key)` constraint, with `read_at` controlling its unread badge. `NotificationPreference` stores per-user channel choices for calendar, tasks, notes, weather, and tools (shared vocabulary lists); missing rows deliberately mean all category channels enabled for backwards compatibility, while the global `Profile.notify_email` and `Profile.notify_desktop` fields remain master switches. `app/services/notification_preferences.py` is the shared policy layer and must be used by Inbox, e-mail, Web Push, and browser-fallback paths. `app/services/notifications.py` materializes due reminders/tasks and mirrors calendar invitations, note mentions/comments/shares, vocabulary list shares, and detected weather alerts without duplicates. Materialization belongs to the explicit notification-center and delivery/scheduled paths; the global context processor only counts existing unread rows and normal dashboard rendering must not create inbox rows. `/notifications/` backfills existing supported source rows for the current user; opening an item or the explicit state action changes only that user's inbox row. New notification-capable source flows must feed both their delivery channel, when applicable, and `UserNotification`. Web Push uses `WebPushSubscription` per browser/device and a unique `WebPushDelivery` per subscription/inbox row; `app/services/web_push.py` validates provider hosts, honors profile-local quiet hours, retries transient failures, removes HTTP 404/410 subscriptions, and is run by `run_automations`. The settings test action targets only the signed-in user's exact device subscription. Never log endpoints or expose the VAPID private key.

### Tasks

`Task` (`app/models.py`) is a per-user to-do gated by the `tasks` feature flag, with an optional `due_at`, `priority` (none/low/medium/high), a `task_list` FK (null = "Inbox"), a `labels` M2M, and a one-level-only `parent` self-FK for subtasks. `app/services/tasks.py` holds the domain logic — `app/views/tasks_views.py` stays thin, dispatching `form_name` POST branches (`task_add`/`task_toggle`/`task_delete`, plus list/label CRUD) into it, the same single-view-many-branches shape the view already had before lists/labels existed. `get_tasks_context` groups subtasks under their parent (`item.subtasks`) rather than returning a flat list, and derives `due_state`/`status_label`/`status_tone` plus counts (`all`/`open`/`done`/`overdue`/`today`/`upcoming`) per item; `today` includes overdue-and-open, `upcoming` is the next 7 days.
- `TaskForm` declares `task_list`/`parent`/`labels` as querysets scoped to the request user in `__init__` (the same pattern as `CalendarEventForm.attendees`) — this is also what caps subtask nesting at one level: the `parent` field's queryset only offers top-level tasks, so a subtask can never itself be chosen as a parent. There is deliberately no separate service-side re-validation of that constraint; the form's scoped queryset already enforces it.
- Recurrence (`recurrence_rule`: none/DAILY/WEEKLY/MONTHLY/YEARLY, reusing `CalendarEventForm.repeat`'s choices for UI consistency) advances **on completion**, not by bulk-creating a series up front like calendar's `expand_manual_recurrence` — `toggle_task` in `app/services/tasks.py` keeps the completed instance and creates exactly one new sibling with `due_at` stepped forward one cadence unit, `is_done=False`, and blank notified-at columns, so it flows through the existing idempotent notification claiming untouched.
- The Tasks page (`tasks.html`) has a sidebar with smart views (Alle/Heute/Demnächst) and the user's lists, layered as a second client-side filter dimension (`data-task-view`/`data-task-list`) in `tasks.js` alongside the pre-existing state filter (open/done/overdue) — both dimensions combine in `taskMatchesFilter`/`taskMatchesView`. A subtask row inherits its *filter* view/list from its parent (`filter_view`/`filter_task_list_id` in the context dict, distinct from the row's own `view`/`task_list_id` used for its own badge) so it's never hidden orphaned when its parent is filtered out.
- A quick-add control (e.g. "Neues Label") that visually lives inside another `<form>` cannot itself be a nested `<form>` — HTML5 silently drops a `<form>` start tag while one is already open. Such controls instead use the `form="<id>"` attribute to associate their inputs/button with a sibling `<form>` rendered outside the outer one (see the `task-label-quick-add` form in `tasks.html`). Relatedly, a Django `{# ... #}` comment cannot span multiple lines — it silently stops being treated as a comment at all and leaks its raw text (including any `<form>`-like substrings) into the page; use `{% comment %}...{% endcomment %}` for anything longer than one line.
- Calendar task chips are HTML5-draggable (`data-task-drag`); dropping one onto a day or the week grid posts a `task_reschedule` form (built by `calendar.js`, honouring `return_to`) to `reschedule_task`, which keeps the time of day unless dropped on a time slot. Whenever a task's due date moves later — rescheduled or edited — `rearm_task_reminders` clears the notified-at columns and deletes the `task:<pk>` inbox row so every channel fires again at the new time; call it for any new path that changes `due_at`.
- New tasks read their title as quick-add text (`TaskForm._apply_quick_add`, only when `instance.pk` is None): `app/services/quick_add.py` (`parse_quick_add`, stdlib + regex, German) takes out one date phrase, one time, `!hoch`/`!mittel`/`!niedrig`/`!1-3` and `#label` for the user's existing labels. Phrases only count when they stand alone (whitespace or text edge around them), invalid dates stay in the title, a bare passed time means tomorrow, and explicitly filled form fields win over the title. Date-only results get `DEFAULT_DUE_TIME` (09:00).
- `Task.assignee` (top-level tasks only — `TaskForm.clean` rejects it on subtasks) hands a task to another user. `visible_tasks(user)` (own + assigned + subtasks of assigned) is the read/toggle scope; edit, delete, reorder and reschedule stay filtered on `user=` so the assignee can only tick tasks off. Due reminders go to the assignee instead of the owner (`_tasks_due_for`/`_task_recipient` in `app/services/notifications.py`), and assigning creates a `task_assignment` inbox row (`materialize_task_assignment_notifications`, source key per assignee) delivered by e-mail through `send_pending_user_notification_emails`. The calendar shows `visible_tasks` too (`_calendar_task_item.can_move` keeps foreign chips undraggable). Assigned top-level tasks carry `TaskComment`s between owner and assignee (`add_task_comment`, `form_name=task_comment`); each comment notifies the other side via `materialize_task_comment_notification` at write time — deliberately not backfilled, so a new assignee isn't flooded with the old conversation. Authors edit/delete their own comments (`edit_task_comment`/`delete_task_comment`, which also update/drop the comment's inbox row). The assignee can hand a task back (`return_task`, `form_name=task_return`): the assignee is cleared, the owner gets a `task_returned` inbox row (one per return, so the source key carries a timestamp), and the old `task-assignment` row is deleted so a later re-assignment notifies again.
- Status is `is_done` plus `is_in_progress` (`Task.status` → `open`/`in_progress`/`done`); every status change goes through `_apply_task_status` (via `toggle_task` or `set_task_status`, `form_name=task_status`), which keeps `is_in_progress` false on done tasks and spawns a recurring task's next occurrence only on the transition to done. The board (`task_board_columns`, `partials/task_board_card.html`) renders top-level tasks per status next to the list; `tasks.js` switches layout (remembered in `localStorage`), applies the same filters to cards and posts `#task-status-form` on a column drop, while each card's status buttons work without JS.
- `TaskShare` shares a top-level task with several users (`TaskForm.shared_with` → `save_shares` → `update_task_shares`; the subtask restriction lives in `TaskForm.clean`). `visible_tasks` matches shares through a subquery (not a join), so it never returns duplicates — keep it that way. Shared users may change status and comment like the assignee; `task_participants` is the recipient set for `materialize_task_comment_notification`, and a share creates a `task_share` inbox row (`task-share:<task>:<user>`, deleted again when the share ends via `task_share_leave` or unsharing). Due reminders still go only to assignee/owner.
- Time tracking (`app/services/time_tracking.py`): `TaskTimeEntry` rows per user and task; a partial unique constraint allows one running entry (`ended_at` null) per user, so `start_timer` stops the running one first and treats an `IntegrityError` as "the other request won". Only tasks in `visible_tasks(user)` can be tracked, entries are private to their user (every query filters on `user`), spans under `MIN_ENTRY_SECONDS` are dropped on stop, and `_apply_task_status` stops all timers of a task on its transition to done. The row's play/stop button is a submit with `form_name=task_timer` (the row form's own hidden `task_toggle` loses because the submitter comes last); `annotate_task_items` adds `time_label`/`timer_running` to the tasks context. `/tasks/time/` (`task_time_report`) shows `time_report` per ISO week (`?week=2026-W45`) or month (`?month=2026-11`, one bar per clipped ISO week), with `&format=csv` for a `;`-separated BOM'd CSV; per-list and per-label sums appear only when they split the time (a multi-label task counts for each label), and the weekly summary e-mail lists last week's total and top three tasks when the `tasks` flag is on with `TaskTimeEntryForm` for manual minutes; the "läuft seit" clock is ticked client-side by `task_timer.js`.
- `TaskTemplate` (per owner, at most `MAX_TASK_TEMPLATES`) stores a top-level task's title, priority, list, labels and its subtask titles as a checklist; `save_task_template` snapshots an own task, `create_task_from_template` creates a fresh task plus subtasks (one by one, so their `created_at` keeps the checklist order) with an optional `due_at` from `TaskTemplateUseForm`.
- Due tasks follow the same idempotent email/desktop notification pattern as calendar reminders (`send_due_task_reminder_emails`, `claim_due_desktop_tasks` in `app/services/notifications.py`) — see Notification idempotency above. The dashboard's `tasks` widget (see Dashboard customization below) shows a summary and is gated by the same flag.

### Vacation planner

`app/services/vacation_planner.py` computes German vacation-day accounting per user per year: `VacationYear` (allowance + federal-state `subdivision`), `VacationPeriod` (booked ranges), `OfficialHoliday` (state public holidays, generated via `holidays.country_holidays("DE", ...)` with a hand-written `_fallback_public_holidays` stdlib fallback when the package is absent), `CustomHoliday`, and `HolidayOverride` (per-user day-value adjustments to an official holiday). `calculate_period` walks a date range day-by-day to net out weekends and holiday credit against the required vacation days, split per calendar year (a period can span a year boundary); `annual_summary`/`month_summary`/`month_calendar` build the read views. `app/views/vacation_planner_views.py` holds one view per form (year, period, custom holiday, override) plus a JSON `vacation_preview` endpoint the client calls before submitting a period. Gated by the `vacation_planner` feature flag.

### Tools

`/tools/` is a hub of small everyday helpers gated by the `tools` feature flag; its cards come from `TOOLS` in `app/view_models.py` (an entry with `url_name=None` renders as "Bald verfügbar"). Add a new tool by giving it a view under `/tools/<name>/`, re-exporting it from `app/views/__init__.py`, and setting its catalog `url_name`. The habit tracker (`/tools/habits/`, `app/services/habits.py`) keeps `Habit` (daily/weekly, a `.tone-*` color) plus one `HabitCheck` row per ticked day (unique `(habit, date)`); a weekly habit counts as done when any day of its ISO week is checked, and `current_streak` doesn't break on a still-open today. Only today and the six days before can be toggled (`toggle_habit_check`), via the `habit_toggle` `form_name` POST, which honours `return_to` for the dashboard's `habits` widget. The focus timer (`/tools/focus/`) is purely client-side (`app/static/js/focus_timer.js`, settings in `localStorage`); it measures against an end timestamp so throttled background tabs stay exact, and its pure helpers (`window.LunoraFocusTimer`) are covered by `frontend/focus_timer.test.js`.

The UML class diagram editor: `UmlDiagram` (per owner, not shared) stores the whole diagram as JSON in `document`. **Never trust client JSON**: `app/services/uml_content.py` (`validate_uml_document`) rebuilds it against exact key sets, kind/color/visibility allowlists, length and count limits, and relation endpoint rules. Rendering, editing and all exports (PNG/SVG/PlantUML/Java/JSON) run client-side in `app/static/js/uml.js` (plain script, hand-written SVG), with pure DOM-free helpers in `app/static/js/uml_format.js` exposed as `window.LunoraUmlFormat` and covered by `frontend/uml_format.test.js` (loaded through `node:vm`). `LIMITS` and `relationAllowed` in that file mirror the server validator — change both sides together, or saves start failing with 400. Relation markers always sit at the **target**: for aggregation/composition the target is the whole. Saves are last-write-wins `PUT`s to `uml_diagram_api` (debounced autosave); create/duplicate/delete are normal `form_name` POSTs on `uml_diagrams`.

The vocabulary trainer (`VocabularyList` → `VocabularyCard`, per owner) keeps list/card CRUD as server-rendered `form_name` POSTs on `vocabulary_list_detail`, with domain logic in `app/services/vocabulary.py`: `parse_bulk_cards` (tab > `;` > `=` delimiter per line, all-or-nothing import with line-numbered errors) and `review_card`, the **server-authoritative** Leitner step (correct → box+1, wrong → box 1, `due_at` from `LEITNER_INTERVAL_DAYS`). The practice page (`app/static/js/vocabulary.js`) gets all cards as `json_script`, runs the round client-side, and posts exactly one review per card per round — on the *first* attempt, deferred until the user moves on so "War doch richtig" can flip it; in-round repeats of wrong cards never touch the server. Answer checking (`checkAnswer`) and distractor picking are pure helpers exported as `window.LunoraVocabulary` (the file skips its DOM part when there is no `document`) and tested in `frontend/vocabulary.test.js`.

Habits (`app/services/habits.py`) can carry a `reminder_time` in the owner's local time: `materialize_due_habit_reminders` (run by `run_scheduled_tasks` under the `tools` flag and by the inbox backfill) creates one `habit_reminder` inbox row per habit and day (`habit:<pk>:<date>`) once that time has passed while the habit is still open — weekly habits only on Sunday — and `toggle_habit_check` deletes unread reminders when the habit is ticked off. Each card's "Statistik" comes from `habit_stats` (heatmap of `HEATMAP_WEEKS` Monday-started weeks, total, best streak via `longest_streak`, 30-day or 12-week rate), computed from the checks `habit_items` already loads; phones hide the older columns in CSS. Forms with `data-confirm="…"` get a confirm prompt from `base.js`.

Vocabulary lists can be shared read-only (`VocabularyListShare`, resolved by exact e-mail/username in `share_list`). Leitner progress lives on the cards, so recipients never practice the owner's list: they see it under "Mit dir geteilt" and `copy_list` clones it into their own lists with fresh progress. Every owner-scoped view keeps filtering on `owner=request.user`; only the copy/leave branches look at `shares__user`. A new share notifies the recipient through `materialize_vocabulary_share_notifications` (inbox, plus e-mail/Web Push under the `tools` preference category).

### Dashboard customization

`app/services/dashboard.py` defines the fixed widget catalog (`DASHBOARD_WIDGETS`), each with a template, CSS class, `default_size`, per-widget `options` (with their defaults) and optional `feature_flag`. A user's saved layout (`Profile.dashboard_layout` JSON, version 4: `{version, order, hidden, widgets: {id: {size, tone, ...options}}}`) is passed through `normalize_dashboard_layout` on read (drops unknown IDs and invalid setting values, appends missing widgets, fills defaults, and upgrades older layouts — v2's `wide` list becomes `size: "full"`, v3's `large` (then two thirds of the width) becomes `full`; `home` then persists the upgraded layout) and `validate_dashboard_layout` on write (rejects anything that doesn't exactly cover the current widget set or carries an unknown setting/value — `_setting_error` is the single allowlist for sizes, tones, limits, booleans, periods and quick-action tile IDs) before `dashboard_widgets_for_layout` filters by `feature_flags()` and hidden state. `dashboard_presets()` returns complete, valid layouts ("Übersicht", "Fokus", "Kompakt") that the editor loads as a draft. Gated by the `dashboard_customization` flag; adding a widget means registering it in `DASHBOARD_WIDGETS` (plus any new option in `_setting_error`) and creating its partial template, which starts with `partials/dashboard_widget_head.html` for the shared header.

The `bookmarks` widget lists the user's own `Bookmark` links (http/https only, enforced in `BookmarkForm`; at most `MAX_BOOKMARKS`); adding and removing go through the POST-only `dashboard_bookmarks` view, which always redirects back to `/home/`. Its add form sits in a `<dialog>` opened by a plus in the widget head: `dashboard_widget_head.html` takes an optional `action_dialog` (a dialog id) and `action_label`, and `home.js`'s `initWidgetDialogs` handles `data-dialog-open`/`data-dialog-close` — reuse that for other widgets with an add action rather than inline forms. A widget added to `DASHBOARD_WIDGETS` shows up for existing users too, because `normalize_dashboard_layout` appends unknown IDs as visible — give it a useful empty state.

Sizes are phone-home-screen footprints on a cell grid in `home.css`, pure CSS: `small` 2×2 cells, `medium` 4×2, `large` 4×4, `full` a whole-width strip at its natural height. The grid has 8 cells across from 1180 px, 4 below (small = half width, everything else full width) and a single natural-height column below 560 px. Rows are `minmax(var(--dashboard-row), auto)`, so a widget whose content needs more room grows its rows and its neighbours stretch along instead of leaving holes, and `grid-auto-flow: dense` backfills gaps. Keep the defaults and presets adding up to full 8-cell rows. A widget `tone` adds `has-tone tone-<name>` and the widget's accents read `--widget-tone`/`--widget-tone-strong`, falling back to the profile accent. List widgets load `MAX_WIDGET_ITEMS` rows and the template marks rows past the widget's `limit` `hidden`, as do unchosen quick-action tiles and weather's second day, so the editor previews option changes client-side without a reload. "Zuletzt genutzt" orders its tiles by `lunora-recent-sections` in `localStorage` (written by `base.js` on every authenticated page) — no server-side tracking.

The `notifications` widget (`dashboard_notifications.html`) surfaces the latest already-materialized unread `UserNotification` rows (`app/services/notifications.py`'s read-only `dashboard_latest_notifications`) with an inline "gelesen" action; open tasks (with an inline "erledigt" action) live only in the `tasks` widget. A hidden notifications widget skips the notification query. These reuse the existing `notification_toggle_read` and `task_toggle` endpoints rather than a new AJAX layer — both now accept an optional POST `return_to` (validated with `url_has_allowed_host_and_scheme`, must be a local path) so the action redirects back to the dashboard instead of navigating to the notifications/tasks page; omit it and they fall back to their original page-local redirect. Any future "act without leaving the dashboard" affordance should follow this `return_to` convention rather than introducing fetch/AJAX.

### Command palette

`app/templates/app/partials/command_palette.html` (included in `base.html` for signed-in users) is a `<dialog>` of plain links, gated by `feature_flags` like the navigation; `initCommandPalette` in `base.js` opens it on Ctrl/Cmd+K, filters entries by their text plus `data-keywords` (case- and accent-insensitive), and falls back to `/search/?q=` for the typed text. A new page or settings section that users navigate to belongs in that partial.

### Static asset versioning

Static CSS/JS entry files are cache-busted with a content hash rather than Django's `ManifestStaticFilesStorage`: `app/templatetags/static_versioning.py`'s `{% versioned_static %}` appends `?v=<sha256-of-file-contents>` to a `{% static %}` URL, and `{% static_version %}` combines several files into one digest (used for the service worker's cache name in `service-worker.js`). Every page template must `{% load static static_versioning %}` and use `versioned_static` instead of `static` for its own CSS/JS entry assets. Vite chunks are imported by content-hashed filename instead. `deploy/nginx-lunora.conf` gives query-versioned assets and hashed files under `js/bundles/chunks/` a one-year immutable cache, while unversioned static assets and `/media/` remain at one hour. Static subresources referenced from CSS need an explicit version query because template tags cannot rewrite CSS `url(...)` values. Inter, Font Awesome and KaTeX's stylesheet and fonts are self-hosted under `app/static/vendor/` — no CDN, so formulas keep their styling offline. `npm run vendor:katex` (`scripts/vendor-katex.mjs`) re-copies KaTeX from `node_modules` with woff2-only `?v=katex-<version>` font URLs; rerun it after bumping `katex`, or `StaticVersioningTests.test_vendored_katex_stylesheet_matches_installed_katex` fails. Keep the Font Awesome stylesheet non-blocking via `media="print"` + `onload="this.media='all'"` and retain the `<noscript>` fallback. Don't switch it back to a `rel="preload"` swap: under the service worker Chrome can't reuse the preload ("cross-world service worker resource mismatch") and fetches the stylesheet twice on every page.

### Service worker offline caching

`app/templates/app/service-worker.js` precaches only the app shell (`APP_SHELL_URLS`: the offline page, its CSS, and brand icons) at install time — it must never gain a hardcoded personal-page path (`/notes/`, `/messages/`, `/calendar/`, `/home/`, media URLs); `PwaTests.test_service_worker_does_not_precache_personal_pages_or_media` enforces this. Beyond the shell, every same-origin full-page navigation (`request.mode === "navigate"`) goes through `servePage()`: network-first, and on a successful (`.ok`) response the page is also written into the separate `PAGES_CACHE` so the same URL can still open while offline, trimmed to `MAX_CACHED_PAGES` most-recent entries. `PAGES_CACHE` and `STATIC_CACHE` are both named with the same `{% static_version %}` hash, so a deploy that changes shell CSS/JS also drops old page snapshots (avoiding offline pages that reference static assets no longer being generated). Because the pages cache holds whatever authenticated content a user last viewed, the service worker intercepts the `POST /logout/` form submission and clears `PAGES_CACHE` once it completes, so a signed-out session's pages can't resurface for the next person on a shared device. Runtime `/static/*` asset caching (`serveStaticAsset`) is unrelated and untouched by this — it's cache-first, keyed by either a query-versioned entry URL or a content-hashed Vite chunk URL.

### Audit log

`AuditLogEntry` rows (`app/services/audit_log.py`, `record(action, request, actor=..., summary=...)`) back the superuser-only "Audit-Log" on `/administration/` (`audit_log_page`, filters `all`/`security`/`logins`/`warnings`, 50 per page). Logins, logouts and failed logins come from Django's auth signals (`connect_signals` in `AppConfig.ready`); everything else is recorded at its call site (registration, password reset confirm, 2FA enable/disable/recovery codes, session revokes, calendar feed reset/disable, data export, account deletion before `delete_account`, system settings changes with the changed switches, emergency logout). `record` writes in its own savepoint and never raises. Summaries are short German text and must never contain secrets (tokens, codes, passwords); a failed login only gets an actor when the typed identifier matches exactly one account, otherwise just "Unbekanntes Konto" — the typed text is never stored. `actor_label` keeps the e-mail after the account is deleted (FK `SET_NULL`). The IP comes from `LUNORA_CLIENT_IP_HEADER` (e.g. `CF-Connecting-IP`, only behind a proxy every request passes) or `REMOTE_ADDR`, validated with `ipaddress`. `run_scheduled_tasks` purges entries older than `AUDIT_LOG_RETENTION` (180 days). A new security-relevant action gets an `ACTION_*` constant (plus migration for the choices) and a `record` call.

### Health check

`/healthz/` (`healthz` in `core_views.py`, `app/services/health.py`) is public, GET-only and `never_cache`: it checks the database, the cache and the `AutomationHeartbeat` row that `run_automations` touches after every pass (overdue after three intervals, at least five minutes), answers 200/503 with only fixed status words, and logs causes server-side. The automations check only counts where `LUNORA_HEALTH_REQUIRE_AUTOMATIONS` is on (default: production). It is in `SECURE_REDIRECT_EXEMPT` so host-local monitors can use plain HTTP; never add versions, hostnames or exception text to its body.

## Configuration

`lunora/settings.py` reads a plain `.env` at the repo root with its own tiny parser (`load_env_file`, `os.environ.setdefault` — real environment variables win) plus `env_bool`/`env_int`/`env_list` helpers. `.env.example` is the documented reference. With `DJANGO_DEBUG=false`, missing `DJANGO_SECRET_KEY` or `DJANGO_ALLOWED_HOSTS` raises `ImproperlyConfigured`, and the HTTPS/HSTS/secure-cookie toggles default to on.

Do not commit `.env`, `db.sqlite3`, `media/`, or `private_media/`.

## Testing

Python tests live in the `app/tests/` package, one `test_<area>.py` module per area (Django `TestCase` + test client), grouped into per-area classes; shared fixtures and fake HTTP responses sit in `app/tests/helpers.py`. Tests assert observable behavior: status codes, redirects, rendered templates, context contents, JSON payloads, form validation, and service return values. External HTTP is stubbed with local fake response classes (`FakeJsonResponse`, `FakeWeatherResponse`, `FakeWeatherTileResponse`) patched over the service's fetch helper — no network in tests. `TEST_RUNNER` (`lunora/test_runner.py`) points `MEDIA_ROOT` and `PRIVATE_MEDIA_ROOT` at a temporary directory for the whole run, so uploads made by tests never land in the real media folders, and swaps in the MD5 password hasher — with the production PBKDF2 cost every user-creating test took about two seconds and the suite ran for hours, so don't add per-class `PASSWORD_HASHERS` overrides; `PrivateNoteStorage` resolves its location lazily so such overrides reach it. Close streaming responses (`FileResponse` downloads) you don't consume, or the open file blocks temp-dir cleanup on Windows. Model changes need a migration plus test coverage.
