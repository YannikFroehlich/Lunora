# Notes

Moved out of CLAUDE.md, which keeps the summary and the cross-cutting rules ([CLAUDE.md](../../CLAUDE.md)).

- Documents are Tiptap ProseMirror JSON in `Note.document`. **Never trust client JSON**: `app/services/note_content.py` re-validates every node/mark against explicit allowlists (node types, mark types, fonts, sizes, line heights, hex colors, size/depth/node-count limits) and derives `plain_text` server-side. `Note.save()` itself derives `checklist_done`/`checklist_total` (taskItem counts, shown as a badge on note list cards) whenever `document` is written, so any new write path stays consistent as long as it lists `document` in `update_fields`. Adding an editor feature means extending both `frontend/notes.js` and that allowlist. Checklist items carry an optional `dueDate` (`YYYY-MM-DD`, `DatedTaskItem` in `frontend/notes.js`, chip attributes from `dueDateAttributes` in `checklist-utils.js`), shown by every export through `task_due_label`. Math is a `mathInline`/`mathBlock` node holding a raw `latex` string (length-capped, rendered client-side with KaTeX) validated the same way. KaTeX is dynamically imported on the first formula render; do not turn it back into an eager top-level import.
- Concurrency is optimistic on `Note.revision` for plain saves (other API clients, renames from the list, the editor once live editing broke). A stale `base_revision` raises `NoteConflictError` → HTTP 409 with `{"error": "revision_conflict", "note": ...}`; the client resubmits with `conflict_resolution: true`. The editor itself saves through live editing (below), which has no conflicts. `NoteVersion` snapshots are written on interval/restore/conflict and pruned.
- Pin/archive/color/icon/folder live in `NoteUserState`, not on `Note`, because notes are shared and these are per-viewer — the same shared note can sit in a different folder, or be pinned, for its owner and each person it's shared with. `accessible_notes()` annotates `state_is_pinned`, `state_is_archived`, `is_shared_with_user`, `has_unseen_share`, `state_color`, `state_icon` — query through it (or `get_accessible_note`) rather than `Note.objects` so permission scoping and those annotations stay consistent. `set_note_style` validates `color`/`icon` against `NoteUserState.COLOR_CHOICES`/`ICON_CHOICES` before saving. Tags (`NoteTag`, `set_note_tags` via the `tags` note action) are per viewer too; `#tag` in a search is split off by `split_tag_filters` and applied with `filter_by_tags` before `search_notes`, in the notes list and in `global_search`. The list view loads every note's tags in one query (`note_tags_by_note`, set as `note.viewer_tags`), so `serialize_note` doesn't ask per note.
- Folders (`NoteFolder`, self-referential `parent`, depth capped by `FOLDER_MAX_DEPTH`) and notes share one ordered tree per user. `move_note_tree_item` handles drag-and-drop moves (`before`/`after`/`inside`/`root`) and re-indexes the affected container via `_reindex_tree_container`; `_validate_folder_move_destination` blocks moving a folder into its own descendant. A note can be created from a built-in template (`NOTE_TEMPLATES`) or a per-owner custom one (`NoteTemplate`, saved from an existing note via `create_note_template`).
- Attachments are stored under `PRIVATE_MEDIA_ROOT` via `private_note_storage`, addressed by UUID `file_id`, and only served through `note_attachment_download`, which re-checks note access. They are never under `MEDIA_URL`.
- PDF export renders server-side with reportlab (`app/services/note_pdf.py`); Markdown export (`app/services/note_markdown.py`) is a plain server-side renderer of the same document, and Word export (`app/services/note_docx.py`, hand-written WordprocessingML on `zipfile`) is the counterpart of `docx_import.py` — keep the schema's child order in `w:pPr`/`w:rPr`/`w:tcPr`/`w:tblPr` or Word reports the file as corrupt. All three go through `_note_export`'s access check so permissions apply to exports too.
- Search goes through `app/services/note_search.py` (`search_notes`), used by both the notes list and `global_search` — never re-filter with `icontains` at a call site. It dispatches on `connection.vendor`: PostgreSQL matches a weighted `tsvector` (`title` A, `plain_text` B, `german` config) ranked with `SearchRank`; SQLite falls back to substring matching with an equivalent SQL-side rank. Both share `parse_search_query` (bare words AND, `"phrases"`, `-exclusions`) so behaviour matches. Two things are deliberate: terms are matched as `:*` prefixes **and** kept as substrings, because German compounds mean "Rakete" must find "Raketenstart" and "start" must too; and the weighted tsvector is stored in `Note.search_vector` (`SearchVectorField`, GIN index `app_note_search_vector_gin`), refreshed by `Note.save()` via `refresh_note_search_vectors` whenever `title`/`plain_text` are written (PostgreSQL only — on SQLite the column stays NULL and the index isn't created; migration 0071 creates it and backfills conditionally). A raw `queryset.update()` of title/plain_text bypasses `save()`, so call `refresh_note_search_vectors` there; until then such a note is still found through the substring branch. `django.contrib.postgres` is in `INSTALLED_APPS` for the field and index. Terms fed to `search_type="raw"` must stay bare words (`^\w+$`) or PostgreSQL raises a query-time error. Because the test suite runs on SQLite, `NotePostgresSearchSqlTests` compiles the production SQL against a PostgreSQL backend to cover that branch.
- `frontend/notes.js` builds to the ES-module entry `app/static/js/bundles/notes.js` and content-hashed files in `app/static/js/bundles/chunks/`; all of them **are committed**. `vite.config.js` separates editor core, Tiptap extensions, syntax highlighting, and the lazily imported KaTeX renderer. After editing anything in `frontend/`, run `npm run build` and commit the regenerated entry plus the complete chunk directory so stale hashed chunks are removed. `notes.html` must load the entry with `type="module"`, and `lunora/settings.py` keeps `.js` mapped to `application/javascript` for Django's Windows development server. `npm test` (vitest) only covers `frontend/**/*.test.js` — the small pure helpers.
- The editor toolbar (`notes.html`) keeps only the most-used controls (undo/redo/save, bold/italic/underline/strike, lists) always visible; everything else sits behind two `data-toolbar-tab="text"|"insert"` tabs (`activateToolbarTab` in `notes.js`, modeled directly on `settings.js`'s `activateSettingsSection`) toggling sibling `data-toolbar-panel` groups. This works with zero changes to command dispatch because `runCommand`/`applyFormatControl`/`updateToolbarState` already select every control by its `data-command`/`data-format` attribute rather than DOM position — moving a button between panels never breaks it. The code-language `<select>` (`data-code-language-group`) deliberately stays a *sibling* of both panels, not nested inside one, because its visibility is driven by cursor position (inside/outside a code block), independent of which tab is active. `openFormatControl` (used when a keyboard shortcut like Alt+Shift+F targets a `[data-format]` control) activates that control's owning tab first if it's currently hidden, so shortcuts never silently focus a `display:none` element.
- Code blocks get syntax highlighting via `@tiptap/extension-code-block-lowlight` plus individually imported `highlight.js` grammars registered with `lowlight` (StarterKit's own `codeBlock` is disabled via `codeBlock: false`). Do not switch back to `lowlight`'s larger `common` bundle. The toolbar's language options, the registered grammar keys, and `note_content.py`'s `ALLOWED_CODE_LANGUAGES` must stay aligned, or a saved language can either fail highlighting or server-side validation.
- `@`-mentions are a `mention` atom node (`{userId, label}`) built on `@tiptap/suggestion` (no `tippy.js` — the popup is a manually positioned `<div>`, matching `messages.js`'s context-menu pattern). The suggestion list (`note_mention_candidates_api`) and the server-side save-time check (`_validate_mention_references` in `app/services/notes.py`) both restrict candidates to users who already have access to the note (owner + `NoteShare` rows) — mentioning someone without access is rejected, not auto-shared.
- Fill-in fields are a `formField` atom node (`{placeholder, value}`, plain strings capped by `MAX_FORM_FIELD_PLACEHOLDER`/`MAX_FORM_FIELD_VALUE`, `marks: ""` because the server only accepts marks on text). Its node view in `frontend/notes.js` is a real `<input>` that writes `value` back with `setNodeAttribute`, so typing saves like any edit. `docx_import.py` makes them from Word content controls (`w:sdt` of the text/rich-text/date/list kinds; `w:showingPlcHdr` content becomes the placeholder) and legacy `FORMTEXT`/`FORMDROPDOWN` fields, and `note_docx.py` writes them back as plain-text content controls; PDF, Markdown and the public page show an empty one as `FORM_FIELD_BLANK`.
- Note-to-note links are a `noteLink` atom node (`{noteId, label}`); `note_link_candidates_api` suggests targets from `accessible_notes()` and `_validate_note_link_references` re-checks the same access at save time, the same pattern as mentions. `save_note` diffs the document's `noteLink` references against `NoteLink` rows (`_set_note_links`) to keep backlinks in sync without a stored reverse index. The same rows feed the graph page `/notes/graph/` (`note_graph` → `note_link_graph`, drawn by the plain script `app/static/js/note_graph.js` with its own force layout): only non-trashed notes from `accessible_notes()` and links between two of them, undirected, best-connected first and capped at `MAX_GRAPH_NOTES` because the layout is O(n²).
- Inline comments are a `commentThread` mark (`{threadId}`, a client-generated UUID) plus `NoteCommentThread`/`NoteComment` rows. `save_note` cross-checks every `commentThread.threadId` found in the document against real `NoteCommentThread` rows for that note, the same way it already does for attachment/mention references — a document can't reference a thread it never created via `note_comments_api`. `duplicate_note` strips `commentThread` marks from the copy (`_strip_comment_marks`) because the new note has no threads of its own yet; forgetting that step makes the duplicate un-savable.
- The editor page (`.note-editor-page` in `notes.css`) is plain white paper with black text, independent of the color theme, so document colors look as in Word. Dark mode imitates Word's: the page keeps its light colors and is inverted as a whole with `filter: invert(1) hue-rotate(180deg)` (on the page, not `.tiptap`, which would become the containing block of floating images); anything drawn on the page that must not flip (`img`, `pre`, attachment/mention/link chips, the image layout menu) carries the same filter again. A new non-document element inside the page needs adding to that list. Table cells/headers carry optional `backgroundColor`, `borderColor` (`#rrggbb` or `none`) and `borderLeft` (`ShadedTableCell`/`ShadedTableHeader` in `frontend/notes.js`), paragraphs/headings optional `backgroundColor`/`borderLeft`/`borderBottom` (`BlockBox`, `BLOCK_BOX_ATTRIBUTES` in `note_content.py`); only `#rrggbb` is parsed back from HTML, matching the server allowlist, and `note_html.py` renders the same styles.
- Public read-only links: `Note.public_token` (null = not public) is managed only by the owner through `note_public_link_api` (`set_note_public_link`; POST on/rotate, DELETE off) and gated by the `note_public_links` flag. `/s/notes/<token>/` (`note_public`, no login) renders the note server-side with `app/services/note_html.py` — a second trust boundary that escapes everything and re-checks styles/colors/link schemes against `note_content.py`'s allowlists, renders mentions and note links as plain labels, and drops comment marks — and its files go through `note_public_attachment`, which only serves attachments of that same note. Both send `Referrer-Policy: same-origin` (not `no-referrer`, which makes browsers send `Origin: null` and fails CSRF for same-origin forms such as logout) and `X-Robots-Tag: noindex`. The token is a credential like `calendar_feed_token`: keep it out of exports, duplicates and logs. Trashed notes and inactive owners 404. Formulas render client-side through the separate Vite entry `frontend/note_public.js` → `app/static/js/bundles/note_public.js`, loaded only when the note contains math; there is no syntax highlighting on the public page.
- Live editing (`app/services/note_collab.py`, `frontend/collab.js`, no Y.js): a central step log in the style of prosemirror-collab, over HTTP polling of `note_collab_api` (every second while others are there, else every five, right after local changes). Editors send the ProseMirror steps they made on top of the version they know; `sync_note` numbers and stores them as `NoteStep` rows only when that version is the newest (under the note row lock), otherwise it answers with the missing steps and the client rebases (`rebaseSteps`, `receiveTransaction`) and sends again. The server never applies steps, so `validate_note_steps` in `note_content.py` checks everything a step adds (slice content through `_validate_node`, marks, attribute values against `NODE_ATTRIBUTES`; attribute steps may not touch `attachmentId`/`userId`/`noteId`) plus the same reference checks as a save; a new editor feature that produces a new step type or attribute needs adding there too. `client_id` is `<user id>-<tab>`, set by the server. `Note.document` is a snapshot: `save_note(..., collab_version=V)` stores the confirmed document at step version V without the revision check (`collab.snapshot()` sends pending steps first), an older snapshot only keeps its title, and steps older than `COLLAB_STEP_HISTORY` behind it are pruned. Any other document write (plain save, version restore) calls `_reset_collab`, which empties the log and jumps `collab_version` past it, so open editors get `resync` and reload. Mentions arriving through steps notify their author at step time; snapshot saves don't notify. Cursors are cache-only (`CURSOR_TTL_SECONDS`) and drawn as decorations; remote transactions carry the collab plugin meta (`isRemoteTransaction`) so they don't mark the note dirty. "Wer hat was geschrieben": on shared notes (`Authorship` in `frontend/collab.js`, configured with `viewer_id` only when the note has shares) an `appendTransaction` gives text that a local change inserted (`insertedRanges`) an `author` mark `{userId}` — not for remote steps, undo/redo (`history$` meta) or `setContent` calls that carry `KEEP_AUTHORS` (draft restore, conflict load); the mark is allowlisted in `note_content.py`, travels with the steps, colors text by `cursorTone` while the `authors` toggle is on (legend in the status bar, remembered in `localStorage`), is ignored by the exports and the public page, and is stripped from saved templates. It is informational, not proof: pasted or moved text becomes the paster's.
- Presence: `note_presence_api` pings every 15 s (`NoteViewerPresence`, TTL `NOTE_PRESENCE_TTL_SECONDS`); `?editing=1` marks keystrokes since the previous ping (`is_editing`, only honoured for users who `can_edit_note`), and `notes.js` pings at once on the first keystroke after a quiet spell, so the others see "bearbeitet gerade" (`editingLabel` in `frontend/presence-utils.js`).
- Shared folders (`NoteFolderShare`, `app/services/note_folder_shares.py`, page `note_folder_share` at `/notes/folders/<id>/share/`) don't add a second access path: they keep `NoteShare` rows in step, marked with `via_folder` (the shared folder; null = shared by hand, never touched). `sync_note_shares(note)` recomputes a note's folder-made rows from the *owner's* placement only: the owner's notes in a shared folder or below go to every member in their role; an editor's own notes in their `mirror` (a folder of their own, created on sharing and named uniquely) or below go to the folder owner (editor) and the other members. Every path that changes the owner's placement must re-sync — `create_note`, `set_note_folder`, `move_note_tree_item` (whole subtree for folders via `sync_folder_tree`) already do, and `delete_note_folder` ends the shares first (`end_shares_of_deleted_folder`; deleting a mirror = leaving). `share_note` turns a folder-made row into a manual one. One `note_folder_share` inbox row per folder share, none per note.
- Daily notes: `/notes/today/` (`note_today` → `open_daily_note` in `app/services/daily_notes.py`) opens the user's note for their local today, created on first use with a `noteLink` to the previous daily note (plus its `NoteLink` row), today's appointments and the open tasks due by today as plain bullet lists (not checklists, so ticking in the note never pretends to finish a task) and an empty "Notizen" section. `Note.daily_date` marks it (unique per owner while set); a trashed daily note is opened in the trash rather than recreated.
- Note reminders (`NoteReminder`, one per note and person, set/cleared through `note_reminder` from the bell dialog in `notes.html`, whose card and bell button are soft regions) are turned into `note_reminder` inbox rows by `materialize_due_note_reminders` (run_automations under the `notes` flag and the inbox backfill) and deleted; a reminder whose note was trashed or unshared is dropped.
- "Checkliste als Aufgaben" (`checklistTasks` command → `checklist_tasks` note action → `create_tasks_from_checklist` in `app/services/tasks.py`) turns open `taskItem`s into the user's own Inbox tasks linked to the note (`Task.note`, `dueDate` at `DEFAULT_DUE_TIME`), skipping titles that already exist as open tasks; it and the `present` command save pending edits first because both read the stored document.
- Presentation mode: `/notes/<id>/present/` (`note_present`) splits the document with `render_note_slides` (`note_html.py`, the same escaping renderer as the public page) at top-level headings of level 1/2 and horizontal rules; `app/static/js/note_present.js` (plain script) shows one slide at a time with keys, swipe and the Fullscreen API, and the slides simply stack without JavaScript.
- Both mentions and comments notify through the shared `NoteActivityNotification` model (`kind` = `mention`/`comment`) — see Notification idempotency below.
- Linked tasks and events (`app/services/linked_notes.py`): `Task.note` and `CalendarEvent.note` (`SET_NULL`) are set by the owner — the task edit dialog's "Verknüpfte Notiz" select (`linkable_notes`), the event detail page's `event_note` form, or the checklist action. Every side names only what the viewer may open: the note's "Verknüpft mit" footer lists `note_linked_items` (tasks through `visible_tasks`, own and invited events), a task row or event names its note only if `readable_note_ids` contains it, and a trash restore drops a link to a note that is gone or no longer accessible.
