# Tools

Moved out of CLAUDE.md, which keeps the summary and the cross-cutting rules ([CLAUDE.md](../../CLAUDE.md)).

`/tools/` is a hub of small everyday helpers gated by the `tools` feature flag; its cards come from `TOOLS` in `app/view_models.py` (an entry with `url_name=None` renders as "Bald verfügbar"). Add a new tool by giving it a view under `/tools/<name>/`, re-exporting it from `app/views/__init__.py`, and setting its catalog `url_name`. The habit tracker (`/tools/habits/`, `app/services/habits.py`) keeps `Habit` (daily/weekly, a `.tone-*` color) plus one `HabitCheck` row per ticked day (unique `(habit, date)`); a weekly habit counts as done when any day of its ISO week is checked, and `current_streak` doesn't break on a still-open today. Only today and the six days before can be toggled (`toggle_habit_check`), via the `habit_toggle` `form_name` POST, which honours `return_to` for the dashboard's `habits` widget. The focus timer (`/tools/focus/`) runs client-side (`app/static/js/focus_timer.js`, settings and the chosen task in `localStorage`); it measures against an end timestamp so throttled background tabs stay exact. With the `tasks` flag on it offers the user's open `visible_tasks`, and a running focus phase POSTs `action=start|stop` to the same view, which calls `start_timer`/`stop_timer` (stop only touches the running entry when it is on that task; leaving the page sends the stop as a beacon), and its pure helpers (`window.LunoraFocusTimer`) are covered by `frontend/focus_timer.test.js`.

The UML class diagram editor: `UmlDiagram` (per owner, not shared) stores the whole diagram as JSON in `document`. **Never trust client JSON**: `app/services/uml_content.py` (`validate_uml_document`) rebuilds it against exact key sets, kind/color/visibility allowlists, length and count limits, and relation endpoint rules. Rendering, editing and all exports (PNG/SVG/PlantUML/Java/JSON) run client-side in `app/static/js/uml.js` (plain script, hand-written SVG), with pure DOM-free helpers in `app/static/js/uml_format.js` exposed as `window.LunoraUmlFormat` and covered by `frontend/uml_format.test.js` (loaded through `node:vm`). `LIMITS` and `relationAllowed` in that file mirror the server validator — change both sides together, or saves start failing with 400. Relation markers always sit at the **target**: for aggregation/composition the target is the whole. Saves are last-write-wins `PUT`s to `uml_diagram_api` (debounced autosave); create/duplicate/delete are normal `form_name` POSTs on `uml_diagrams`.

Whiteboards (`/tools/whiteboard/`) follow the UML editor's shape: `Whiteboard` (per owner, shareable) keeps `{version, elements}` in `document`, where the list order is the z-order and each element is a `stroke` or `highlight` (flat `[x1, y1, x2, y2, …]` points; the highlighter is the same data drawn four times as wide and translucent — use `isStroke`/`lineWidth`, not `type === "stroke"`), `line`, `arrow`, `rect`/`ellipse` (`x, y, w, h, fill`), `text`, or `sticky` (`x, y, w, h, text`: tinted paper from `STICKY_PAPER`, text wrapped by `wrapText`, may be empty, edited through the same text field as `text`). **Never trust client JSON**: `app/services/whiteboard_content.py` (`validate_whiteboard_document`, built on `uml_content.py`'s helpers) checks exact key sets per type, named colors, the widths 2/4/8, text sizes and the per-stroke and total point limits. The editor (`app/static/js/whiteboard.js`) draws hand-written SVG on light paper in both themes; its pure helpers (`window.LunoraWhiteboardFormat` in `whiteboard_format.js`, tested by `frontend/whiteboard_format.test.js`) simplify strokes on pen-up and do the geometry (bounds, hit tests across the eraser's swept segment, moves rounded like the server). `LIMITS`/`COLORS`/`WIDTHS` there mirror the validator, and `WhiteboardTests.test_client_limits_mirror_the_validator` fails when they drift. Undo stores only what a change took out and put in (`{index, element}` lists), so elements are replaced by changed copies, never mutated. The eraser has two modes (a select, remembered in `localStorage`): whole elements, or cutting the touched part out of strokes with `eraseFromStroke`; it changes the board while dragging and `finishErase` records the difference to the board as the gesture found it as one undo step. Enter on the canvas inserts the current shape (or a text field) in the middle — the keyboard route for the drag-only tools. A single selected element shows grips (`handlePoints`) that `resizeElement` drags; the optional grid (`localStorage`) snaps shape drawing, moves and resizes but not the pen. Copy/paste goes through `localStorage` so it works across boards; pasted elements only have to be drawable, the server validates on save. The editor saves through live editing: `flush` turns every change since the last one into operations with `diffElements` (`put` an element, optionally `after` an anchor id — `null` is the bottom, an unknown id the top, no `after` keeps its place; `move` an id after an anchor; `delete`; `title`) — only elements outside the longest run that kept its order get moved — and POSTs them with a per-tab `seq` to `whiteboard_sync_api` (`sync_whiteboard` in `app/services/whiteboards.py`). The server cleans each operation (`clean_whiteboard_op`), applies them in arrival order under the row lock with `apply_whiteboard_ops`, validates the resulting board, stores it (`revision` += operations) plus one `WhiteboardOp` per operation (`OP_HISTORY` kept), skips operations whose `seq` it already has, and answers with every operation after the editor's `version` (its own included), `acked` and `whiteboard_hash` of the board. The editor keeps `confirmed` (the server's board) and shows it plus its own pending operations; because everyone applies the same operations in the same order to the elements exactly as the server cleaned them, all editors show the same board, and the hash proves it — a mismatch reloads the board. `applyOps`/`canonicalJson`/`boardHash` in `whiteboard_format.js` mirror `apply_whiteboard_ops`/`whiteboard_hash`; change both sides together (`frontend/whiteboard_live.test.js` and `WhiteboardLiveTests.test_hash_matches_the_editor` share a fixture hash). During a drag (`interaction`) the board isn't swapped — the others' changes show once it's finished — shared boards poll every second, and a refused push drops the pending operations and reloads. Each poll also carries the editor's pointer in board coordinates and whether it is drawing; `_exchange_peers` keeps them per board in the cache (`PEER_TTL_SECONDS`, members only, own user left out) and returns `peers`, which `whiteboard.js` shows as avatars in the header (`renderPresence`, "… zeichnet gerade") and as named pointers in the overlay (`drawPeers`, gliding by CSS transition, counter-scaled to keep their screen size). Comments (`WhiteboardComment`, `app/services/whiteboard_comments.py`, `whiteboard_comments_api`) are threads pinned to board coordinates: a root comment carries `x`/`y` and `resolved_at`, replies point at it through `parent`; every member may comment, reply and resolve/reopen (a reply reopens), authors delete their own (the root takes the thread and its `whiteboard-comment:<pk>` inbox rows with it). Each new comment notifies the other members (`materialize_whiteboard_comment_notification`, category tools, e-mailed with the whiteboard shares, its URL `?comment=<thread>` opens the popover). The `comment` tool (C) places a draft on release (Enter: in the middle); pins and the popover are HTML over the canvas (`renderComments`/`positionComments`), and the sync answer's `comments` signature (`comments_signature`) tells editors when to reload them. `PUT whiteboard_api` (whole board against `Whiteboard.revision`, 409 on a stale `base_revision`) stays for API clients; it adds no operations, so open editors get `resync` and reload. `WhiteboardShare` gives other users the owner's drawing rights (`whiteboard_share`/`_unshare`/`_leave` on the overview; only the owner shares, unshares and deletes); `accessible_whiteboards(user)` is the access check every board query goes through (shares via a subquery, so no duplicates). A share creates a `whiteboard_share` inbox row (`whiteboard-share:<pk>`, dropped when the share ends). `Whiteboard.save()` derives `plain_text` (the text elements) whenever `document` is written, for the global search; PNG/SVG/JSON export and JSON import run client-side, and the image exports embed the vendored Inter font as a data URL because an SVG image can't load page fonts. The overview's thumbnails come from `app/services/whiteboard_preview.py`, a second renderer into HTML that escapes through `format_html`, takes colors from its own table and thins strokes to `MAX_PREVIEW_POINTS`; a new element type needs adding there, in the validator and in `elementNode`.

Whiteboard extras: "Neues Whiteboard" offers `WHITEBOARD_TEMPLATES` (`app/services/whiteboard_templates.py`, plain element lists that pass the validator). Lines and arrows may carry optional `from`/`to` (`OPTIONAL_KEYS` in `whiteboard_content.py`, element ids, never the own id): `finishShape`/`finishResize` bind an end dropped on a shape (`bindableAt`, `BIND_PIXELS`), and `commit` runs `withBoundArrows`, which re-routes every connector bound to a changed or removed shape (`routeConnector`/`borderPoint` in `whiteboard_format.js`, `CONNECTOR_GAP` mirrored by the templates) and adds those arrows to the same change, so they sync and undo with it; during a drag `previewBoundArrows` shows stand-ins on `connectorLayer`; a moved connector keeps only bindings to shapes moved with it (`moveWithSelection`). The server never routes, so bindings are informational there. Pictures are `image` elements (`x, y, w, h, file`) pointing at a `WhiteboardImage` (`add_whiteboard_image`: validated like note images, `ensure_storage_available`, `MAX_BOARD_IMAGE_BYTES` per board) served only to members by `whiteboard_image`; uploads go through `whiteboard_image_upload_api` (toolbar button or drop on the canvas), exports inline them as data URLs (`inlineImages`), the thumbnail draws a placeholder, `copy_whiteboard_images` really copies them on duplicate, and `delete_whiteboards`/`delete_account` remove the files on commit — a new path deleting boards must use `delete_whiteboards`. The laser tool (K) draws a fading trail (`LASER_MS`) that is never stored: it rides along the sync poll as `laser` (`_clean_laser`, `MAX_LASER_POINTS`), comes back in `peers`, and shared boards poll every `LASER_POLL` while a trail shows.

Kanban boards (`/tools/kanban/`, `app/services/kanban.py`, `kanban_views.py`): `KanbanBoard` → `KanbanColumn`/`KanbanLane` (swimlanes, at least one of each) → `KanbanCard` (column, lane, `position` inside that cell, optional color/due date/assignee). One server-rendered soft region (`#kanban-board`) with `form_name` POSTs; `KanbanCardForm` scopes column, lane and assignee to the board and its members, so moves and assignments can't leave the board. `KanbanBoardShare` works like whiteboard shares (`accessible_boards` subquery, members edit everything, only the owner shares/deletes, `kanban-share:<pk>` inbox row); assigning a card to someone else creates a `kanban-card:<card>:<user>` row, and leaving clears the leaver's assignments. Every POST ends with `touch_board`, and shared boards poll `?version=1` every five seconds and swap the region through `window.lunoraSwapSoftRegions` (`base.js`) unless a dialog, menu or typed text is open. `kanban.js` drags cards with HTML5 drag and drop and offers Alt+arrow keys as the keyboard route; the last column counts as done, so its cards are never overdue.

Retrospectives (`/tools/retro/`, `app/services/retro.py`, `retro_views.py`): `RetroBoard` (phase `collect`→`group`→`vote`→`discuss`→`done`, limits, `hide_cards`/`hide_votes`/`anonymous`, `presented_card`, `join_token`) → `RetroColumn` (from `TEMPLATES`) → `RetroCard` (`group` stacks a card under another, one level deep) → `RetroVote` (one row per dot, on the group's top card) and `RetroAction` ("Actions": `title`, optional multi-line `description`, an `assignee` among the board's participants, guests included; every participant adds and edits them through `retro_action_add`/`retro_action_edit`, the owner deletes; optional `task` once a Lunora user takes it over, which copies title and description). A board may follow up on one of its owner's own earlier retros (`previous`, from `previous_choices`: never a retro the owner only joined, so participants never see foreign actions; the create form preselects the newest). While collecting, that retro's actions sit beside the columns, and any participant ticks them off through `retro_action_done`, whose lookup `reviewable_actions` covers only the board's own and its `previous` board's actions. `action_done` is the action's state: the task's `is_done` once one exists (then `set_action_done` refuses), else `RetroAction.done`. Everyone on a board is a `RetroParticipant`: Lunora users by account, guests by name, and the invite link `/retro/join/<token>/` is the only way in (no login needed; a signed-in visitor joins with their account). Guests are identified by `request.session["retro_guests"]` (board id → participant id); `participant_for` is the single access check and `retro_board` therefore has no `login_required`. Guest pages carry `noindex`, `Referrer-Policy: same-origin` and `private, no-cache`; joins are throttled per IP and every POST per participant with `count_hit`. While collecting with `hide_cards`, other people's card text is never rendered (server-side); with `hide_votes` only one's own votes show before the discussion. The view checks phases for every card change, not just the template: edit/delete only while collecting, group/ungroup only while grouping; `can_change_card` lets the owner change others' cards only once they are revealed. Card authors show from the grouping phase on (never while collecting) and never on `anonymous` boards. Once votes show on a non-`anonymous` board, each card's vote count carries its voters' names as a `title` tooltip (`voters`). Owner-only forms are listed in `OWNER_FORMS`. The page is one soft region (`#retro-board`) polled every three seconds like kanban; `retro.js` opens the presented card as a modal for everyone (owner closes it with a backdrop click, Escape or "Beenden"), groups cards by drag and drop (keyboard route: the "Gruppieren mit …" select), and runs the timer from `data-ends-at`. While discussing, `RetroCard.discussed` ticks topics off: `present_card` marks the previously presented card once the owner moves on (forward, back or closing), and the owner-only `retro_discussed` sets it by hand on the group's top card (`set_discussed`); the bar counts `discussed_count` of `topic_count`. The page never scrolls; columns and the actions panel scroll inside. No global search area (hidden cards) and no notifications; the export holds the owner's retros without the token.

Recipes (`app/services/recipes.py`) have a per-owner weekly meal plan (`MealPlanEntry`, at most `MAX_MEALS_PER_DAY` per day) on the recipes page (`?week=2026-W46`, parsed by `time_tracking.week_start_for`); `add_week_to_list` sends every planned recipe's ingredients through `add_ingredients_to_list`, so shared ingredients merge on the list. `MealPlanEntry.servings` (null = the recipe's own) scales a recipe with `servings` to the sum planned that week via `scale_quantity` (every number in the quantity, as a `Fraction`); recipes without servings still count once. `add_ingredients_to_list` passes `merge=add_quantities` to `add_shopping_item`, so an open item's quantity is added up (plain "<number> <unit>" only, g/kg and ml/l convert, anything else is joined with " + "); manual adds and ticked-off items still replace the quantity. The recipe page takes `?servings=` (`_wanted_servings`, 1–99, only for recipes with servings) and rescales its display and the shopping POST. The recipe page's "Kochmodus" (`app/static/js/cook_mode.js`, a full-screen `<dialog>`) shows the preparation one step at a time — `instruction_steps` in `recipes.py` splits it into paragraphs, or lines when there are no blank lines, without leading "1."/"Schritt 2:" — with arrow-key navigation, the (scaled) ingredients, and the Screen Wake Lock API keeping the screen on while it is open where the browser allows it. `recipe_import.py` imports a recipe from a URL: the page is fetched through `app/services/safe_fetch.py` and only its schema.org/Recipe JSON-LD is read (`parse_recipe_page`, stdlib `html.parser`), throttled per user with `count_hit`; the result still passes `RecipeForm`, and `Recipe.source_url` keeps the address.

`app/services/safe_fetch.py` is the shared SSRF boundary for fetching user-supplied URLs (`normalize_url`, `fetch(url, read, …)`): calendar subscriptions and the recipe import both go through it, so a new feature that fetches a URL a user typed in must too. `read` runs while the deadline cut is still armed; `read_capped` caps the size. Its `FetchError` messages never contain the URL (`SubscriptionError` is an alias).

Shared expenses (`app/services/expenses.py`, `/tools/expenses/`): `ExpenseGroup` with `ExpenseGroupMember`s who all have the same rights (add expenses and members, delete expenses); nobody removes anyone else, `leave_group` needs a zero balance and deletes an empty group. An `Expense` stores explicit `ExpenseShare` amounts (`split_amount` gives leftover cents to the first people), so later member changes never re-split old expenses, and people are `SET_NULL` so a deleted account leaves the others' balances intact. A settlement is an expense with `is_settlement`, paid by the debtor and owed by the creditor; only one of the two may record it, and only for a payment `settle_up_plan` currently suggests. Adding someone creates an `expense_group` inbox row (`expense-group:<group>:<user>`), deleted when they leave. `split_amount` splits by weights (largest remainder gets the leftover cents): `ExpenseForm`'s `split_mode` "shares"/"amounts" read one `split_<user id>` field per person into `weights`, and fixed amounts are just weights that add up to the total. A `RecurringExpense` ("Jeden Monat wiederholen") stores those weights as strings plus `day_of_month`; `post_due_recurring_expenses` (run by `run_scheduled_tasks` under the `tools` flag and on every group page view) claims each month with a conditional update of `next_on` before adding it, catches up missed months (`MAX_CATCH_UP` per pass), drops people who left and deletes the rule once the payer or everyone sharing it has left. `Expense.category` (`CATEGORY_CHOICES`/`CATEGORY_ICONS`, also on `RecurringExpense`) feeds `month_overview` (settlements left out), shown per `?month=2026-11` on the group page. `?format=csv` on a group page exports its expenses (`expenses_csv`, cells starting with a formula character get a leading `'`).

The shopping list (`ShoppingItem`, aisles from the emoji catalog in `app/services/shopping.py`) scans barcodes through `shopping_scan` (`app/services/shopping_products.py`): `normalize_barcode` checks the GTIN check digit (UPC-A becomes EAN-13) before anything reaches the lookup URL, a new barcode is looked up server-side on Open Food Facts (`lookup_open_food_facts`, stdlib `urllib`, size/time capped, answers cached for all users, new lookups throttled per user with `count_hit`) and stored as the owner's `ShoppingProduct` (text and numbers only, no photos), so later scans never leave the server. "shop" mode ticks off the item scanned with that barcode before or one whose word stems all appear in the product name (`find_open_item`); "add" mode puts the product on the list. A list can be shared (`ShoppingListShare`, `app/services/shopping_lists.py`): every user has exactly one list, `?list=<owner id>` opens a shared one and `list_owner_for` is the access check every item query and `shopping_scan` go through; members have the owner's rights on items, only the owner shares/unshares (`shopping-share:<pk>` inbox row, dropped again when the share ends). Toggles post the wanted `done` state so two people ticking at once agree — which is also why `shopping.js` may queue them: its capture-phase submit listener takes every `shopping_toggle` away from the soft submit, shows the change at once, keeps it in `localStorage["lunora.shoppingQueue"]` (keyed by list URL and item) and replays it on `online` or every 15 s, then swaps in the list region (`reloadList`, shared with the live poll, which re-applies still-queued changes); and a shared page polls `?version=1` (`list_version`, a hash of the items) every five seconds and swaps in the `[data-shopping-live]` region when it changed. The scanner in `shopping.js` uses the browser's `BarcodeDetector` (no library; iOS Safari has none, so typing the number is the fallback) and reloads the list when the dialog closes.

Wish lists (`/tools/wishlist/`, `app/services/wishlist.py`, `wishlist_views.py`): `WishList` → `WishListItem` (details read from the shop page through `safe_fetch`, Amazon by its own reader, other shops from JSON-LD/OpenGraph; pictures only via `wish_item_image`, re-encoded server-side) with a `WishListItemPricePoint` per distinct price (`record_price_point`, drawn as an inline SVG by `sparkline_points`). Items carry a `priority` (sorted by `sorted_items`) and an optional `target_price`: `refresh_due_prices` (run_automations, `tools` flag) re-reads only items with a target, each at most every `PRICE_CHECK_INTERVAL` and `MAX_PRICE_CHECKS_PER_RUN` per pass, stamping `price_checked_at` before fetching so a refusing shop isn't asked every pass; a new price point that crosses the target from above creates a `wish_price_alert` inbox row (`wish-price:<point>`, category tools). `WishListShare` gives other users read access (`accessible_wish_lists`, subquery; `wish-list-share:<pk>` inbox row); members only reserve/release items (`WishListReservation`, one per item, the unique constraint decides races) or leave, which drops their reservations. Reservations are a surprise: only the member branch of `wish_list_detail` reads them, the owner's page, totals and data export never do — keep it that way for any new owner-facing path. Members don't see items with quantity 0.

Contracts & subscriptions (`/tools/contracts/`, `Contract`, `app/services/contracts.py`): a contract with `term_months` runs from `start_date` for that term, then extends by `renewal_months` at a time and must be cancelled `notice_days` before the running term ends (`next_deadline` → `Deadline(cancel_by, ends_on)`, the first one on or after today); without a minimum term it is cancellable any time with the notice period. `cancelled_on` makes `end_date` the first term end still reachable on that day, and ended contracts drop out of the totals (`monthly_cost` per `MONTHLY_FACTOR`). `materialize_due_contract_reminders` (notifications.py, imported lazily because contracts → expenses → notifications) creates one `contract_deadline` inbox row per deadline once it is `remind_days` away (`contract:<pk>:<cancel_by>`), run by run_automations under the `tools` flag and the inbox backfill. The page renders every form from `partials/contract_fields.html` without ids, because each card has its own edit form.

Lunora Wrapped (`/wrapped/?year=`, `app/services/wrapped.py`): `year_in_review` counts the user's own activity in the calendar year of their time zone, per feature flag, one slide per area with something to show; tasks have no completion time, so done tasks count by `updated_at`. The page reuses the presentation deck (`note_present.js`, deck styles in `note_public.css`).

The vocabulary trainer (`VocabularyList` → `VocabularyCard`, per owner) keeps list/card CRUD as server-rendered `form_name` POSTs on `vocabulary_list_detail`, with domain logic in `app/services/vocabulary.py`: `parse_bulk_cards` (tab > `;` > `=` delimiter per line, all-or-nothing import with line-numbered errors) and `review_card`, the **server-authoritative** Leitner step (correct → box+1, wrong → box 1, `due_at` from `LEITNER_INTERVAL_DAYS`). The practice page (`app/static/js/vocabulary.js`) gets all cards as `json_script`, runs the round client-side, and posts exactly one review per card per round — on the *first* attempt, deferred until the user moves on so "War doch richtig" can flip it; in-round repeats of wrong cards never touch the server. Answer checking (`checkAnswer`) and distractor picking are pure helpers exported as `window.LunoraVocabulary` (the file skips its DOM part when there is no `document`) and tested in `frontend/vocabulary.test.js`.

Habits (`app/services/habits.py`) can carry a `reminder_time` in the owner's local time: `materialize_due_habit_reminders` (run by `run_scheduled_tasks` under the `tools` flag and by the inbox backfill) creates one `habit_reminder` inbox row per habit and day (`habit:<pk>:<date>`) once that time has passed while the habit is still open — weekly habits only on Sunday — and `toggle_habit_check` deletes unread reminders when the habit is ticked off. Each card's "Statistik" comes from `habit_stats` (heatmap of `HEATMAP_WEEKS` Monday-started weeks, total, best streak via `longest_streak`, 30-day or 12-week rate), computed from the checks `habit_items` already loads; phones hide the older columns in CSS. Forms with `data-confirm="…"` get a confirm prompt from `base.js`.

Vocabulary lists can be shared read-only (`VocabularyListShare`, resolved by exact e-mail/username in `share_list`). Leitner progress lives on the cards, so recipients never practice the owner's list: they see it under "Mit dir geteilt" and `copy_list` clones it into their own lists with fresh progress. Every owner-scoped view keeps filtering on `owner=request.user`; only the copy/leave branches look at `shares__user`. A new share notifies the recipient through `materialize_vocabulary_share_notifications` (inbox, plus e-mail/Web Push under the `tools` preference category).

Bookmarks (`/tools/bookmarks/`, `app/services/bookmarks.py`, `bookmark_views.py`): `Bookmark` (per owner, http/https only via `BookmarkForm`, at most `MAX_BOOKMARKS`) carries `tags` (lower-case, space-separated, normalized by `normalize_tags`) and a `description`. `add_bookmark` reads the page once through `safe_fetch` (`fetch_page_preview`, throttled per user with `count_hit`; Open Graph title/description, else `<title>`/`<meta name="description">`, only up to `</head>`), fills a blank name from the page title or the host, and saves even when the page can't be read. `/tools/bookmarks/export/` (`export_bookmark_file`) writes all of the owner's bookmarks as one flat Netscape bookmark file, tags in the `TAGS` attribute, which `import_bookmark_file` reads back. The dashboard widget (`dashboard_bookmarks`, also the share target's "Als Lesezeichen") and the page share that service; the widget lists the first `DASHBOARD_BOOKMARKS` and links to the page. The page filters with `?q=` (the search syntax, via `filter_by_query`) and `?tag=`, edits inline, and "Vorschau neu laden" refetches the description. Tests patch `fetch_page_preview` or `safe_fetch.fetch` — never let one reach the network.

`import_bookmark_file` reads a browser's Netscape-format bookmark export (no page fetches; folders become one tag each, the toolbar/"other bookmarks" root folders are dropped, only http(s) URLs, existing URLs skipped, capped at `MAX_BOOKMARKS`). `check_due_links` (run by `run_automations` under the `tools` flag) requests up to `MAX_LINK_CHECKS_PER_RUN` bookmarks not checked for `LINK_CHECK_INTERVAL` through `safe_fetch`, sharing the per-user preview throttle; a failing request sets `unreachable_since`, an answer (or a successful "Vorschau neu laden") clears it. `?broken=1` lists the marked ones.

`add_bookmark` and the edit form refuse an address the user already saved (`find_duplicate`, ignoring a trailing slash; other users' bookmarks don't count). Bookmarks have no trash, so the `bookmark_delete_broken` action under the "Nicht erreichbar" filter deletes every marked one for good behind a `data-confirm`.
