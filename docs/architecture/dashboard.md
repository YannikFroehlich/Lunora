# Dashboard customization

Moved out of CLAUDE.md, which keeps the summary and the cross-cutting rules ([CLAUDE.md](../../CLAUDE.md)).

`app/services/dashboard.py` defines the fixed widget catalog (`DASHBOARD_WIDGETS`), each with a template, CSS class, `default_size`, per-widget `options` (with their defaults) and optional `feature_flag`. A user's saved layout (`Profile.dashboard_layout` JSON, version 4: `{version, order, hidden, widgets: {id: {size, tone, ...options}}}`) is passed through `normalize_dashboard_layout` on read (drops unknown IDs and invalid setting values, appends missing widgets, fills defaults, and upgrades older layouts — v2's `wide` list becomes `size: "full"`, v3's `large` (then two thirds of the width) becomes `full`; `home` then persists the upgraded layout) and `validate_dashboard_layout` on write (rejects anything that doesn't exactly cover the current widget set or carries an unknown setting/value — `_setting_error` is the single allowlist for sizes, tones, limits, booleans, periods and quick-action tile IDs) before `dashboard_widgets_for_layout` filters by `feature_flags()` and hidden state. `dashboard_presets()` returns complete, valid layouts ("Übersicht", "Fokus", "Kompakt") that the editor loads as a draft. Gated by the `dashboard_customization` flag; adding a widget means registering it in `DASHBOARD_WIDGETS` (plus any new option in `_setting_error`) and creating its partial template, which starts with `partials/dashboard_widget_head.html` for the shared header.

The `meal_plan` (today's and tomorrow's `MealPlanEntry` rows) and `expenses` (own balance per group, debts first) widgets are two mediums appended as one full row, hidden in the Fokus and Kompakt presets. The `countdown` widget (a full-width strip at the end of the default layout, hidden in the Fokus and Kompakt presets) lists the user's `Countdown` dates from today on (at most `MAX_COUNTDOWNS`, added and removed through the POST-only `dashboard_countdowns` view like bookmarks; `CountdownForm` refuses past dates and uses the `countdown_` id prefix because the bookmark form on the page has a `title` too) plus, with the `vacation_planner` flag, the next or running vacation (`_dashboard_countdowns` in `view_models.py`). The `bookmarks` widget lists the user's own `Bookmark` links (http/https only, enforced in `BookmarkForm`; at most `MAX_BOOKMARKS`); adding and removing go through the POST-only `dashboard_bookmarks` view, which always redirects back to `/home/`. Its add form sits in a `<dialog>` opened by a plus in the widget head: `dashboard_widget_head.html` takes an optional `action_dialog` (a dialog id) and `action_label`, and `home.js`'s `initWidgetDialogs` handles `data-dialog-open`/`data-dialog-close` — reuse that for other widgets with an add action rather than inline forms. A widget added to `DASHBOARD_WIDGETS` shows up for existing users too, because `normalize_dashboard_layout` appends unknown IDs as visible — give it a useful empty state.

Sizes are phone-home-screen footprints on a cell grid in `home.css`, pure CSS: `small` 2×2 cells, `medium` 4×2, `large` 4×4, `full` a whole-width strip at its natural height. The grid has 8 cells across from 1180 px, 4 below (small = half width, everything else full width) and a single natural-height column below 560 px. Rows are `minmax(var(--dashboard-row), auto)`, so a widget whose content needs more room grows its rows and its neighbours stretch along instead of leaving holes, and `grid-auto-flow: dense` backfills gaps. Keep the defaults and presets adding up to full 8-cell rows. A widget `tone` adds `has-tone tone-<name>` and the widget's accents read `--widget-tone`/`--widget-tone-strong`, falling back to the profile accent. List widgets load `MAX_WIDGET_ITEMS` rows and the template marks rows past the widget's `limit` `hidden`, as do unchosen quick-action tiles and weather's second day, so the editor previews option changes client-side without a reload. "Zuletzt genutzt" orders its tiles by `lunora-recent-sections` in `localStorage` (written by `base.js` on every authenticated page) — no server-side tracking.

The `notifications` widget (`dashboard_notifications.html`) surfaces the latest already-materialized unread `UserNotification` rows (`app/services/notifications.py`'s read-only `dashboard_latest_notifications`) with an inline "gelesen" action; open tasks (with an inline "erledigt" action) live only in the `tasks` widget. A hidden notifications widget skips the notification query. These reuse the existing `notification_toggle_read` and `task_toggle` endpoints rather than a new AJAX layer — both now accept an optional POST `return_to` (validated with `url_has_allowed_host_and_scheme`, must be a local path) so the action redirects back to the dashboard instead of navigating to the notifications/tasks page; omit it and they fall back to their original page-local redirect. Any future "act without leaving the dashboard" affordance should follow this `return_to` convention; the widget bodies are soft regions (below), so these actions don't reload the page.
