# Accounts and security

Login, two-factor, passkeys, data export/import, storage quota and sessions. The summary and the cross-cutting rules are in [CLAUDE.md](../../CLAUDE.md).

`normal_login_enabled` is separate: when off, only staff/superusers may authenticate (`EmailLoginForm.confirm_login_allowed`) and registration returns 503. `EmailLoginForm` resolves the identifier as either e-mail or username. Registration is protected by Cloudflare Turnstile (`app/services/turnstile.py`, `verify_registration_token`), which fails closed when `CLOUDFLARE_TURNSTILE_REQUIRED` is on and is skipped when it is off (default: on unless `DJANGO_DEBUG`).

Central sign-in ("Mit yfserver-Konto anmelden", `login_sso` → Keycloak → `login_sso_callback`) is an OpenID Connect code flow with PKCE in `app/services/oidc.py`, hand-rolled on `urllib`; it is on when `OIDC_ISSUER`, `OIDC_CLIENT_ID` and `OIDC_CLIENT_SECRET` are set. The ID token comes straight from the token endpoint over TLS, so issuer, audience, expiry and nonce are checked, not its signature. The token request must send its own `User-Agent`: Cloudflare in front of `auth.yfserver.de` blocks urllib's default one (error 1010). Accounts are found by `Profile.oidc_subject`; the first sign-in links an existing account only through a *verified* Keycloak e-mail (which also clears `email_confirmation_pending`), otherwise a new account without a usable password and a profile are created. When the ID token carries `groups`, membership in `admins` sets `is_staff`/`is_superuser`; `OIDC_REQUIRED_GROUP` refuses everyone else (dev: `dev-access`). `is_active` and `user_can_login` still apply. Lunora's TOTP step is skipped on this path because Keycloak asks for its own second factor. Login alerts (`_notify_login`) and the audit log's login signal run as for a password login. `LunoraLogoutView` sends a user who signed in this way on to Keycloak's `end_session_endpoint` (`id_token_hint` in the session), so the central session ends too; for that redirect `settings.py` adds the issuer's origin to the CSP `form-action` (browsers apply it to redirects after a form POST).

Failed logins count per account and per client (`LOGIN_CLIENT_ATTEMPT_LIMIT`), failed 2FA codes per account; counters go through the atomic `count_hit` in `app/services/throttle.py`, never `cache.get` plus `cache.set`.

Two-factor login is optional TOTP per profile (`app/services/two_factor.py`, RFC 6238 on the stdlib; the setup QR code comes from reportlab's bundled `qrencoder`). `LunoraLoginView.form_valid` does not log a 2FA user in: it parks `{user_id, backend, next, started_at}` in the session and redirects to `login_two_factor`, which checks a TOTP or one-time recovery code under `select_for_update` (`totp_last_step` blocks replays, recovery codes are stored as SHA-256 hashes and consumed) and throttles wrong codes per account through the cache, so restarting the password step doesn't reset the count. `/admin/login/` redirects to Lunora's login so the admin cannot bypass the second factor. A wrong code after a correct password creates a `security_alert` inbox row (`materialize_failed_two_factor_notification`, one per `SECURITY_ALERT_WINDOW`); that kind has no preference category and ignores the e-mail/push master switches, so nobody can mute it. Enabling 2FA calls `revoke_other_sessions`. Clearing `Profile.totp_enabled_at` in the admin resets a locked-out user.

Passkeys (`Passkey`, `app/services/passkeys.py`, `app/static/js/passkeys.js`) stand in for the code at that second step, and also sign in on their own from the login page ("Mit Passkey anmelden": `login_passkey_options` hands out a challenge only on click, so a visit creates no session; `login_passkey` → `passkeys.authenticate`). That passwordless path asks for `userVerification: "required"`, no `allowCredentials`, and checks the UV flag plus the `userHandle` against the stored owner, so the passkey alone is still two factors; it then applies `confirm_login_allowed`'s checks by hand (active, `user_can_login`, e-mail confirmed, TOTP still on) and counts failures on the same per-client `login-client:` counter as wrong passwords. They exist only while TOTP is on — the code and recovery codes stay the way back in — so `two_factor.disable` deletes them and `is_enabled` doesn't look at them. The service is hand-written WebAuthn with "none" attestation: a small CBOR decoder, ES256/RS256 keys stored as PEM, and the checks for ceremony type, challenge, origin, RP id hash, user presence, signature (`cryptography`) and signature counter (0 on both sides = authenticator without counter). RP id and origin come from the request (`relying_party`: `request.get_host()` and `request.scheme`), so a credential belongs to one host name and production needs `DJANGO_USE_X_FORWARDED_PROTO`/`_HOST` to be right. Every challenge is spent by its first attempt: settings keep one in the session (`PASSKEY_CHALLENGE_SESSION_KEY`, popped by `passkey_add`), the login step keeps one inside the pending dict, the passwordless sign-in one under `PASSKEY_SIGN_IN_SESSION_KEY`. Counter updates hold the `Passkey` row lock (`_use_passkey`). A failed passkey answer counts against the same per-account throttle and raises the same `security_alert` as a wrong code. The pages hand the options to `passkeys.js` as a `json_script`; a form with `data-passkey-form="create|get"` (or `data-passkey-options-url` to fetch them by POST) gets the browser's answer written into its `[data-passkey-response]` field and is then submitted normally. `app/tests/test_passkeys.py` has a software authenticator (`FakeAuthenticator`) for new cases.

`/settings/export/` (`app/services/data_export.py`) streams a ZIP of everything the user owns (JSON per area, notes as Markdown, note/chat attachments, UML documents, whiteboards); one per user every two minutes, built in an anonymous file under `PRIVATE_MEDIA_ROOT` because `/tmp` is a RAM disk in production. A new user-owned model belongs in that export too; secrets such as `calendar_feed_token` and the TOTP fields stay out. The counterpart is the `data_import` form on the same tab (`app/services/data_import.py`, stdlib only): Markdown files become notes through a small block/inline parser whose output still passes `validate_note_document` (a leading `# Title` and the export's byline are taken over/dropped, so exported notes round-trip), and `.ics` files become `appointment` events — `CalendarEvent.import_uid` skips VEVENTs imported before, and `RRULE`s expand into a Lunora series through the stdlib expander `_ics_occurrences` (FREQ, INTERVAL, COUNT, UNTIL, BYDAY with month/year ordinals, BYMONTHDAY, BYMONTH, BYWEEKNO as ISO weeks in yearly rules, BYSETPOS per period; occurrences keep DTSTART's wall-clock time), minus `EXDATE`s; VEVENTs with `RECURRENCE-ID` replace (or, when cancelled, remove) their occurrence and join the same `recurrence_id`. Rules with other parts (BYYEARDAY, BYHOUR, …) import their first date and count as `simplified`. `.docx` files (there, and through `note_import` from the notes page's "Neue Notiz" dialog) go through `app/services/docx_import.py`: `zipfile` + `ElementTree` with per-part size limits, a total budget and a DOCTYPE ban, styles/numbering resolved by hand, embedded pictures stored as note image attachments (converted to PNG with Pillow when the attachment validator refuses them).

`SystemSettings.user_storage_limit_mb` (superuser form `StorageLimitForm` on `/administration/`, 0 = no limit) caps the files each user uploaded to notes and chats, summed from `size` by `uploaded_by` (`app/services/storage_quota.py`). Every path that writes a new file for a user calls `ensure_storage_available` first, copies included (note attachments, Word import, `duplicate_note`, chat attachments via `MessageForm`, forwarding); a new upload path needs that call too, or it bypasses the limit.

The same "Sicherheit" tab lists signed-in devices and deletes the account. `UserSession` rows (device User-Agent, last activity) are written by `app.middleware.UserSessionMiddleware` after the view runs (so the login request is tracked with its rotated key), throttled to one write per five minutes via a session marker; the sessions themselves stay in Django's DB session store, and rows whose session is gone are pruned in `active_sessions`. Those rows are the per-user index of sessions: "Alle anderen abmelden" (`revoke_other_sessions`) and the administration page's session stats read them instead of decoding the session table (migration 0063 backfilled sessions from before tracking), so keep every authenticated request flowing through the middleware. Only the superuser emergency logout (`logout_other_authenticated_sessions`) still decodes every session on purpose. `delete_account` (`app/services/accounts.py`) relies on the cascade for rows but must delete note/chat attachment files and the profile image itself — it collects them first and removes them in `transaction.on_commit`. A new model holding user files needs adding there. Superusers can't delete themselves from settings.
